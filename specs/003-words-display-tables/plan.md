## Summary

Precompute four fixed, read-only derived tables for Quran word display —
`quran_words_ordered_tashkeel`, `quran_words_ordered_simple`,
`quran_words_unique_tashkeel`, `quran_words_unique_simple` — built **entirely from the
already-imported Feature 002 tables** (`quran_words` as the source; `quran_ayahs` only
for `verse_key`). The two ordered tables carry one row per **readable** word (77,432
each, ayah markers excluded) with mushaf/surah/ayah ordering and per-display-key
occurrence statistics; the two unique tables carry one row per distinct display text with
statistics and stable first-occurrence fields.

**Technical approach:** EF Core Code-First adds the four tables via a **schema-only
migration**. The existing `tools/QuranDashboard.DataImporter` console host gains a second
verb, **`rebuild-words`**, that derives and populates the tables **DB-to-DB** using
server-side `INSERT … SELECT` with window functions inside **one transaction**. The
rebuild **refuses on non-empty targets unless `--force`** (which truncates only the four
derived tables), **never touches the source tables**, runs a **hard-gated validation
suite before commit** (rolls back on any failure), and emits a **Markdown + JSON report**
every run. No API, UI, search, or linguistic enrichment is in scope.

## Technical Context

**Language/Version**: C# 13 / .NET 10 (`net10.0`)
**Primary Dependencies**: EF Core `10.0.8`, `Npgsql.EntityFrameworkCore.PostgreSQL`
`10.0.0` (server-side `INSERT … SELECT` via raw SQL on the Npgsql connection),
`Microsoft.Extensions.Hosting` `10.0.0` (console host + DI)
**Storage**: PostgreSQL — 4 new read-only derived tables built from the 5 existing
Feature 002 tables (source tables are read-only inputs, never mutated)
**Testing**: xUnit `2.9.3` + FluentAssertions `8.2.0` + Testcontainers.PostgreSql `4.4.0`
(`postgres:16-alpine`) in the existing `tests/QuranDashboard.Tests` project
**Target Platform**: Linux server, .NET 10 runtime
**Project Type**: Existing Backend Clean Architecture solution (7 projects incl. the
`DataImporter` console host) — **no new project**; one new verb + new feature folders
**Performance Goals**: full rebuild (~191k derived rows) completes in seconds via
server-side set-based SQL in one transaction; operator-run batch, not a user-facing path
**Constraints**: schema-only migration (no `HasData`); atomic rebuild (all-or-nothing);
refuse-unless-empty + `--force` (truncates only the 4 derived tables); source tables
never mutated; **no ayah text stored** (identifiers only); grouping on the **exact stored
text** (no normalization); `text_imlaei_simple` stored as a passive reference only — **no
search**; **no API / no request-path work**; Quranic data safety (every run emits a
traceable report; tests use source-safe fixtures)
**Scale/Scope**: 4 derived tables; rows ≈ 77,432 + 77,432 + ~21,210 + ~14,783 ≈ **191k**
(unique counts derived from the DB, not hardcoded); repeatable operator-run rebuild; no
API this feature

**Structure Decision**: Reuse the existing solution. All new types live under
feature folders (`Quran/Words/Display/`, `Quran/Words/RebuildDisplayWords/`) per
`BACKEND_STRUCTURE.md`. The rebuild is an operator action exposed as a new verb on the
existing console host — **not** a new project and **not** an HTTP endpoint. Derivation is
**server-side `INSERT … SELECT`** (the data already lives in PostgreSQL); see research.md
for the rationale and the rejected alternatives.
