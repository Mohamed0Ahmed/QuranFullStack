## Summary

Import the immutable Quran reference data — **114 surahs, 6,236 ayahs, 604 mushaf pages, 9,046 mushaf lines, 83,668 word occurrences** (6,236 ayah-end markers + 77,432 readable words) — into PostgreSQL, with each word carrying its QPC v4 glyph code, three text forms (uthmani-with-tashkeel, uthmani-simple, imlaei-simple), and its page/line/order resolved from the mushaf layout.

**Technical approach:** EF Core Code-First creates the five tables (schema-only migration). A **dedicated console importer** (new project, not an HTTP endpoint) reads a manifest-described source staging tree, assembles the rows in memory, runs a hard-gated validation suite, and — only if validation passes — bulk-inserts via Npgsql binary `COPY` inside a single transaction. Re-runs **refuse on non-empty tables** unless `--force` (atomic truncate-and-reload). Every run emits a validation report (Markdown + JSON). No read API is in scope (deferred to follow-up **001b**).

## Technical Context

**Language/Version**: C# 13 / .NET 10 (`net10.0`)
**Primary Dependencies**: EF Core `10.0.8`, `Npgsql.EntityFrameworkCore.PostgreSQL` `10.0.0` (+ Npgsql binary `COPY` for bulk insert), `System.Text.Json` (source reading), `Microsoft.Extensions.Hosting` (console host + DI)
**Storage**: PostgreSQL — 5 read-only reference tables (`quran_surahs`, `quran_ayahs`, `quran_mushaf_pages`, `quran_mushaf_lines`, `quran_words`)
**Testing**: xUnit (unit) + Testcontainers-for-.NET PostgreSQL (integration/persistence) — see research.md; **no test project exists yet**, one is created in this feature
**Target Platform**: Linux server, .NET 10 runtime
**Project Type**: Backend Clean Architecture solution (6 existing projects) **+ a new CLI import host** (7th project)
**Performance Goals**: full import (~99,668 rows total) completes in well under a few minutes via bulk `COPY` in one transaction; not a user-facing latency path
**Constraints**: migrations contain **schema only** (no data); import is **atomic** (all-or-nothing); **refuse-unless-empty + `--force`**; ayah markers **preserved + flagged**; **Quranic data safety** (never invent/modify source data; every run produces a traceable validation report); **no public/network-exposed import**
**Scale/Scope**: 5 tables; rows = 114 + 6,236 + 604 + 9,046 + 83,668 ≈ **99,668**; one-time + repeatable import; **no API** this feature

**Structure Decision**: Reuse the existing 6-project Clean Architecture solution; add one **console host** (`tools/QuranDashboard.DataImporter`) as the import trigger and one **test project** (`tests/QuranDashboard.Tests`). All Quran types live under feature folders (`Quran/...`) in each layer per `BACKEND_STRUCTURE.md`. Page fonts are **out of scope** for this feature (they belong to a later public Mushaf Reader); `qpc_glyph` is retained on `quran_words` as a lightweight future reference.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| 7th project: `tools/QuranDashboard.DataImporter` (console host) | The import is a heavy, operator-run batch op that must **not** be reachable over HTTP; a console host keeps it off the API surface and CI-runnable. | A guarded API endpoint was rejected (puts a destructive bulk op behind HTTP, violates the "no public import" decision); a startup seeder was rejected (couples import to app boot). |
| New test project `tests/QuranDashboard.Tests` | Import correctness is the whole point; persistence/validation needs real-DB integration tests. | No test project exists; correctness can't be proven without one. |
