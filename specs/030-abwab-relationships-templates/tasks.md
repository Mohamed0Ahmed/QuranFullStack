## How to use this file (read before starting — this is the contract for the implementer)

1. **Reuse the accepted `028` + `029` substrate — do NOT rebuild or fork it.** Already accepted:
   - `028`: tracked `ChangeSet` UoW + `AbwabWriteGuardInterceptor` (rejects no-ChangeSet writes and
     physical deletes), `AbwabAuditedCommitExecutor` (barrier → revision lock → generation check →
     head/ChangeSet → post-commit publication), `AbwabWriteBarrier`, `AbwabRevisionState`,
     `ExpectedTimelineGeneration`, `IServerClock`, `IAbwabRestoreAdapter<TProduct, TSnapshot>` /
     `IAbwabRestoreAdapterDescriptor`, `AbwabWriterRegistry` stabilization guard, the §14.1 frontend
     primitives (`PersistentCache`/IndexedDB, action/conflict) in `src/app/core/`, `@angular/forms`,
     and the Playwright harness in `e2e/harness/`.
   - `029`: `ArabicNameNormalizer` (§5.1) + the shared normalization corpus, `Category`/`Section`
     identity, `ManualProtectionResolution` + `ProtectionResolver`, the **category writer**
     (`AbwabCoreWriteHandler` → `CategoryContentHandler` / `CategoryOrderingHandler`),
     `CategoryRestoreAdapter`, `CategorySubtreeHandler`, and the `features/abwab` data-access/state
     conventions.
2. **Every backend mutation** runs in **one audited `ChangeSet`** through `IAbwabWriteExecutor`,
   carries `ExpectedTimelineGeneration` plus the applicable expected `xmin` / `TemplateRevision` /
   `TreeRevision`, and passes the barrier. Bump `TemplateRevision` **exactly once** per grouped
   template operation; bump `TreeRevision` **exactly once** for a whole template application;
   relationship mutations bump **neither**.
3. **Real infrastructure**: backend correctness tests run against **real PostgreSQL** via the
   existing Testcontainers fixture
   `Backend/tests/QuranDashboard.Tests/Abwab/_Fixtures/PostgresFixture.cs` (xUnit collection
   `AbwabDbCollection`). UI tests run in a **real browser** (Playwright).
4. **EF migrations are generated by EF tooling only** (never hand-written), per `Backend/CLAUDE.md`.
   Each workstream generates **its own** migration so neither waits on the other. After generating
   one, report its migration name + files.
5. **Exact `abwab.*` codes only** — every conflict string `030` uses exists in the Master Plan §11
   catalogue; none is invented, renamed, or remapped. Four §11 strings are **new to the codebase**
   and are declared by this feature's tasks — `abwab.relationship_duplicate` and
   `abwab.relationship_cycle` by T027/T030/T034, `abwab.template_cycle` and
   `abwab.template_revision_stale` by T062/T065/T070 — in `AbwabConflictCodes`, `ApiMessages` +
   `AbwabConflictResponses.WriteConflictMessages`,
   `Backend/tests/QuranDashboard.Tests/Abwab/_Support/ConflictCodeParityTests.cs`, and the frontend
   `abwab-conflict.ts` code union + Arabic message map. Already-present codes reused as-is:
   `abwab.row_stale`, `abwab.timeline_generation_stale`, `abwab.tree_revision_stale`,
   `abwab.manual_protection`, `abwab.category_name_conflict`, `abwab.category_unavailable`,
   `abwab.stabilization_active`. HTTP 400/403 follow the accepted `028`/`029` framework behavior
   (`[ApiController]` validation 400s, `[Authorize]` policy 403s) — no `abwab.*` body code exists
   for them and none is introduced.
6. **Hard invariants** (fail the task if violated):
   - **Exactly TWO new registered adapters** (Relationship, DoorTemplate aggregate). The
     application-event interpreter is **NOT** an adapter and registers **nothing** — it delegates
     real-category inversion to the **single `029` `CategoryRestoreAdapter`** (§8).
   - **Template application writes real categories ONLY through the `029` category writer** — no
     second category writer, no second Category adapter. The writer may be **extended
     behavior-preservingly** (the grouped creation seam of T064) — never forked — and `029`
     single-add behavior is proven unchanged by a regression assertion.
   - **No create-from-real-door path and no cross-door copy path may exist.**
   - Template copying is a **strict allowlist**: name, representative excerpt, description, aliases,
     order, structure — nothing else, ever.
   - **NO drag-and-drop** anywhere, including the template editor.
   - **NO Quran foreign key** — `TemplateNode.RepresentativeQuranExcerpt` is a plain string.
   - Relationship mutations **neither start nor are blocked by** the ordinary 24-hour window.
   - Relationship rows are **never** cascade-deleted by a category subtree delete.
7. **Ground truth** for each task is the matching file under `contracts/` + `data-model.md` (both
   cite the Master Plan §-anchors). Read the referenced contract before coding a task.

## Dependencies & Execution Order

### Order (§18.4)

```
Setup (P1) → Foundational (P2) → { US1 ‖ US2 } → Polish
```

- **US1 (relationships)** and **US2 (templates)** are **parallel by design** — §18.4 permits it, they
  share no schema, no handler, no port, and no migration. Neither blocks the other. (The narrow
  shared-file exceptions are listed under Cross-story coupling.)
- The Spec Kit **exits only when both** have finished **their own adapter and vertical slice**
  (FR-021, SC-018). Completing one workstream is not a feature exit.
- **Polish** runs after both, because the final registry assertion (T077) and the exit confirmation
  (T082) span both adapters. Exception: **T075 (budget freeze) and T076 (contract drift) are
  acceptance gates** — run each as soon as its story's endpoints/UI exist, since §15.3 requires
  budgets frozen **before** a writer or UI is accepted.

### Within each story

- Tests are written **first** and must fail before implementation.
- Domain entities → EF config → permission-catalogue extension → migration (EF tooling) → ports →
  application handlers → API → adapter/interpreter → frontend port/mock → HTTP adapter →
  cache/facade → UI → render components.
- Each workstream generates **its own** migration (T025, T059) after its entity types + configs +
  catalogue extension exist, so table DDL and permission seed ride one migration per workstream.

### Cross-story coupling (the only shared-file points — not `[P]` across stories)

- **`029` category writer** — US2's application handler (T064) calls it through the
  behavior-preserving grouped creation seam extracted from `CategoryContentHandler`; the writer is
  never forked and `029` single-add behavior is proven unchanged by T064's regression assertion.
  US1 does not touch it.
- **§8 registry test file** — US1 (T031) and US2 (T066) each add their adapter to the expected set,
  and T077 finalizes the gate. Same file → sequential.
- **Shared catalogue files** — `PermissionCatalogue.cs` + `abwab-permissions.ts` (T024 vs T058),
  `AbwabConflictCodes.cs` + `ConflictCodeParityTests.cs` (T027 vs T062), `ApiMessages` +
  `AbwabConflictResponses.cs` (T030 vs T065), and `abwab-conflict.ts` (T034 vs T070). Each pair
  touches the same file from both stories → run the two sides sequentially in either order.

### Parallel opportunities

- **Whole stories**: US1 and US2 can be staffed concurrently after Phase 2 (respecting the
  shared-file pairs above).
- **[P] within a story**: the full test suites (T009–T021, T039–T053), the domain entities
  (T022; T054–T056), and the adapter/audit/frontend-port/render tasks that touch distinct files.
- **Not parallel**: EF config → catalogue → migration → handlers within a story; the frontend HTTP
  adapter and facade after the port/mock; anything touching `RestoreRegistryTests.cs`; the
  cross-story shared-file pairs listed above.

## Implementation Strategy

### MVP scope

There is **no single-story MVP** here. §18.4 requires **both** workstreams to finish their own adapter
and vertical slice before the Spec Kit exits, and both stories are **P1**. The useful milestones are
partial-delivery checkpoints, not completion:

- **MVP-A** = US1 complete (relationship slice + Relationship adapter accepted).
- **MVP-B** = US2 complete (template slice + DoorTemplate adapter + interpreter accepted).

Either checkpoint alone is a **partial delivery**. The feature is done only when **both** pass in CI.

### Incremental delivery

1. Setup + Foundational → guards (no-Quran-FK, code-drift, stabilization coverage) + shared builders.
2. US1 **and** US2 in parallel → each: tests first, then schema + catalogue → handlers → API →
   adapter → frontend slice → render components → browser proof.
3. Acceptance gates as each story's surface lands → frozen performance budgets (§15.3) and the API
   contract generation/drift check (§15.2 gate 4).
4. Polish → final §8 registry gate, quickstart end-to-end, READMEs, self-checks, report, exit
   confirmation and handoff to `033`.

### Exit

Complete only when **every** §18.4 exit/acceptance criterion passes in CI; the **Relationship** and
**DoorTemplate aggregate** adapters plus the **application-event interpreter** (with its verified reuse
of the `029` Category adapter) are accepted with **no duplicate registry entry**; **no**
relationship/template writer bypasses the audit/protection/concurrency/stabilization foundation; and
`030` built nothing owned by `027`–`029` or `031`–`034`.
