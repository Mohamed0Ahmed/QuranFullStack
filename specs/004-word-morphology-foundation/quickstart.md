# Quickstart — Quran Word Morphology Foundation

How to stage the local source files, create the schema, run the morphology import, and verify the result.
Prerequisite: the **Feature 002 import has already run** (PostgreSQL holds 83,668 `quran_words`, of which
77,432 are readable).

> Commands are illustrative; run them from the Backend solution root unless noted. The import is
> **source-driven** — it reads local JSON files and joins `quran_words`.

## 1. Stage the local source files (local-only; not committed)

Copy the selected files into the **local, in-repo** path (beside `quran-foundation/`). `resources/` is
already Git-ignored, so these data files stay **local-only** — "copy" means a local file copy, **not**
`git add`/commit/push.

```text
App/resources/import-sources/quran-morphology/
  manifest.json
  README.md
  corpus/quranic-corpus-morphology-qpc-aligned.json
  corpus/corpus-qpc-location-alignment-map.json
  qul/word-root.json
  qul/word-lemma.json
  qul/word-stem-corrected-arabic.json
```

`manifest.json` carries, per file: `role`, `originPath`, `expectedRecordCount`, `fileSizeBytes`,
`sha256`, `notes`. The importer verifies these before the run and re-verifies size/`sha256` after
(`MORPH-SOURCE-UNCHANGED`). The external `~/Desktop/.../resources/morphology` workspace is **read-only
provenance only** and is never read at runtime.

## 2. Create the schema (one-time, schema-only migration)

Per `Backend/CLAUDE.md`, migrations are generated by EF tooling **on explicit request** and contain
**schema only** (no `HasData` — the POS vocabulary is seeded by the importer). After adding the six
entities + EF configurations + `DbSet`s:

```bash
# generate (name illustrative) — review the generated migration before applying
dotnet ef migrations add AddQuranWordMorphology \
  --project infrastructure/QuranDashboard.Infrastructure \
  --startup-project api/QuranDashboard.Api

# apply when ready (only on explicit request)
dotnet ef database update \
  --project infrastructure/QuranDashboard.Infrastructure \
  --startup-project api/QuranDashboard.Api
```

The migration creates exactly: `quran_word_morphology`, `quran_word_morphology_segments`, `quran_roots`,
`quran_lemmas`, `quran_stems`, `quran_pos_tags` (all empty).

## 3. Run the import

```bash
# first import (targets empty) — default source = App/resources/import-sources/quran-morphology/
dotnet run --project tools/QuranDashboard.DataImporter -- import-morphology

# explicit source / custom report directory
dotnet run --project tools/QuranDashboard.DataImporter -- import-morphology \
  --source App/resources/import-sources/quran-morphology --report-out ./reports

# re-import after a prior run (targets non-empty) — must force
dotnet run --project tools/QuranDashboard.DataImporter -- import-morphology --force
```

Behavior:
- Verifies the manifest/source files first; refuses early on any presence/count/size/`sha256` mismatch.
- Refuses if any of the six tables is non-empty and `--force` is absent (nothing changes; prints a
  console message and writes no report artifact).
- `--force` truncates **only** the six morphology tables, then rebuilds in one transaction.
- Never touches `quran_words` (or any Feature 002/003 table) and never writes the source files.
- Seeds `quran_pos_tags` from the in-code dictionary; transliterates each non-empty segment form to
  `form_arabic_normalized` (+ tier); empty forms → `NULL`.
- Validates before commit; on any hard-check failure it rolls back (writes nothing).
- Writes a Markdown + JSON report on every import attempt (success or failure). When `--report-out` is
  omitted the report goes to **`resources/report/words-morphology/`** (relative to the repository root).

## 4. Verify

Read the report (verdict `PASS`, totals, tier distribution, all hard checks ✅) and/or spot-check the DB:

```sql
-- 77,432 morphology rows; no markers
SELECT count(*) FROM quran_word_morphology;                       -- 77432
SELECT count(*) FROM quran_word_morphology m
  JOIN quran_words w ON w.id = m.quran_word_id WHERE w.is_ayah_marker; -- 0

-- segments present; empty forms rendered as NULL (expected 208)
SELECT count(*) FROM quran_word_morphology_segments;              -- ~128219
SELECT count(*) FROM quran_word_morphology_segments
  WHERE form_arabic_normalized IS NULL;                           -- 208

-- every head_pos resolves to the POS vocabulary
SELECT count(*) FROM quran_word_morphology m
  LEFT JOIN quran_pos_tags t ON t.code = m.head_pos
  WHERE t.code IS NULL;                                           -- 0

-- derived dimension counts (reported, not hardcoded)
SELECT count(*) FROM quran_roots;                                 -- <derived>
SELECT count(*) FROM quran_lemmas;                                -- <derived>
SELECT count(*) FROM quran_stems;                                 -- <derived>

-- word-type filtering foundation works directly from stored fields (no UI/API)
SELECT t.category, count(*) FROM quran_word_morphology m
  JOIN quran_pos_tags t ON t.code = m.head_pos GROUP BY t.category;
SELECT verb_tense, verb_voice, count(*) FROM quran_word_morphology
  WHERE is_verb GROUP BY verb_tense, verb_voice;

-- source untouched
SELECT count(*) FROM quran_words;                                 -- 83668
```

## 5. Run the tests

```bash
dotnet test tests/QuranDashboard.Tests
```

Integration tests use Testcontainers PostgreSQL (`postgres:16-alpine`) with **synthetic, source-safe**
single-word fixtures (never real verse passages) to prove per-word morphology, POS resolution, verb
tense/voice (active-by-default), dimension dedup on Arabic with Buckwalter-only → null link, segment
rendering (tiers, empties → `NULL`, deterministic render provenance), refusal/`--force`, atomic rollback
on validation failure, and that source tables **and** source files are unchanged. The Buckwalter→Arabic
map has pure unit tests (no DB) for full charset coverage and deterministic mapping.

## What this feature does NOT do

No API, no UI, no generated Arabic i3rab (Feature 005), no syntactic roles, no `qpcUthmani` offsets, no
physical `quran_verbs` table, no treating `form_arabic_normalized` as Mushaf text, no reading of the
external Desktop research workspace, and no modification of `quran_words` or any Feature 002/003 table.
