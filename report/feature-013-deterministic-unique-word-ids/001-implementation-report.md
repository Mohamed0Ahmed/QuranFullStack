# Feature 013 — Deterministic Unique Word IDs: Implementation Report

> Code/migration/tests only. The local reset/reseed verification phase (§7 of the
> planning report) was **not** executed; it is gated on explicit approval.
> Companion planning report:
> `docs/feature-013-words-roots-explorer/feature-013-deterministic-unique-word-ids-plan.md`.

## 1. Scope delivered

This change set realizes **deterministic, reproducible primary keys** for
`quran_words_unique_tashkeel` and `quran_words_unique_simple`, equal to the
first-occurrence `quran_words.id` (`first_quran_word_id`). The three coupled edits
described in the plan shipped together: EF config → migration → rebuild SQL, plus
new hard checks and tests.

Nothing outside the listed scope was changed:
- No words UI/API, route, pagination, or search changes.
- No changes to Quran text, word text, identity keys (`text_uthmani`,
  `word_key_imlaei_simple`), counters, `first_*` fields, or the ordered tables.
- `first_quran_word_id` column kept (FK-backed; readers still use it).
- The pre-existing `UNQ-EXPECT-TASHKEEL` informational-count discrepancy was not
  touched (out of scope).

### 2.2 Migration — `DeterministicUniqueWordIds`

### 2.3 Rebuild SQL — explicit `id = first_quran_word_id`

- `infrastructure/QuranDashboard.Infrastructure/Persistence/DataPipelines/Quran/Words/DisplayRebuilding/DisplayWordsSql.cs`

`InsertUniqueTashkeel` and `InsertUniqueSimple` now include `id` in the column
list and `SELECT f.first_quran_word_id` as the value. The existing `first_occ`
CTE already computes `first_quran_word_id`, so no CTE changes were needed.
Ordered inserts, link UPDATEs, counters, and `TruncateDerivedTables` are
unchanged. `TruncateDerivedTables`' `RESTART IDENTITY` is now a harmless no-op
for the unique tables (kept per decision R4).

### 2.4 Hard checks — `UNQ-ID-DETERMINISTIC` + `UNQ-ID-UNIQUE`

- `infrastructure/QuranDashboard.Infrastructure/Persistence/DataPipelines/Quran/Words/DisplayRebuilding/DisplayWordsSql.cs` — two new SQL constants.
- `infrastructure/QuranDashboard.Infrastructure/Persistence/DataPipelines/Quran/Words/DisplayRebuilding/SqlDisplayWordsRebuilder.cs` — both wired into `RunHardChecksAsync` as **hard** severity, immediately after `UNQ-COUNT`.

| Check id | Severity | Assertion |
| --- | --- | --- |
| `UNQ-ID-DETERMINISTIC` | hard | `id = first_quran_word_id` for all rows in both unique tables (`COUNT(*) WHERE id <> first_quran_word_id` summed across both tables → expect 0) |
| `UNQ-ID-UNIQUE` | hard | no duplicate ids (`COUNT(*) - COUNT(DISTINCT id)` summed across both tables → expect 0); defense-in-depth since the PK already guarantees uniqueness |

A violation rolls back the rebuild (consistent with all other hard checks).

### 2.5 Tests

- `tests/QuranDashboard.Tests/Quran/WordsDisplay/DisplayWordsDeterministicIdTests.cs` (new) — four synthetic-suite tests:
  - `Rebuild_AssignsDeterministicUniqueIdsEqualToFirstQuranWordId` — every unique row has `id == first_quran_word_id`; anchors a real first-occurrence word per table and asserts equality.
  - `Rebuild_ProducesUniqueIdsWithNoDuplicates` — distinct-id count equals row count.
  - `Rebuild_RepublishesDeterministicIdsIntoQuranWordLinks` — every readable `quran_words` link resolves to the matching unique row (deterministic ids flow through unchanged link UPDATEs).
  - `ForcedRebuildTwice_ProducesIdenticalDeterministicIdMappings` — force-rebuild idempotency on the `(id ↔ identity)` mapping **and** the link values.
- `tests/QuranDashboard.Tests/Quran/WordsDisplay/DisplayWordsRealImportIdentityLinksTests.cs` — new canonical-source test `CanonicalImportRebuild_AssignsDeterministicUniqueIdsEqualToFirstQuranWordId` (determinism + uniqueness against the real import).
- `tests/QuranDashboard.Tests/Quran/WordsDisplay/DisplayWordsValidationSuccessReportTests.cs` — extended to assert `UNQ-ID-DETERMINISTIC` and `UNQ-ID-UNIQUE` appear in the report with `hard` severity and pass.
- `tests/QuranDashboard.Tests/Quran/MushafReader/mushaf-reader-seed.sql` — updated the two unique-row inserts to set `id = first_quran_word_id` explicitly (was relying on DB identity generation; now matches the app-assigned contract). The MushafReader fixture uses `EnsureCreatedAsync`, so the column is non-identity from the current model and the explicit `id` is required.

## 5. Notes / follow-ups

- **Coupling honored.** Config + migration + SQL landed together; the rebuild in
  the tests exercises the explicit-`id` insert and the new hard checks.
- **Determinism is realized by the rebuild, not the migration.** Existing rows
  keep their old identity-generated ids until the next `rebuild-words --force`.
  The local reset/reseed verification phase (§7 of the plan) is the acceptance
  gate for that and was **not** run, per instruction.
- **One adjacent seed-script edit** (`mushaf-reader-seed.sql`) was required
  because it inserted into the unique tables without an `id`, relying on the old
  identity strategy. The fix sets `id = first_quran_word_id`, consistent with the
  new contract. No production/shared DB was affected.
- The pre-existing `UNQ-EXPECT-TASHKEEL` informational warning (expects 21,210,
  DB has 21,294) is unchanged and remains out of scope.
