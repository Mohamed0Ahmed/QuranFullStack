## 6. Root-cause analysis of the enriched import failure

### Symptom
```
Npgsql.PostgresException (0x80004005): 23505: duplicate key value violates
unique constraint "IX_quran_lemmas_first_word_order_in_mushaf"
  …  at MorphologyBulkCopier.CopyLemmasAsync(...) line 76
  …  at EfBulkMorphologyWriter.ImportAsync(...) line 92
Where: COPY quran_lemmas, line 35
```

### Schema fact
`quran_lemmas.first_word_order_in_mushaf` carries a **UNIQUE** index:
`CREATE UNIQUE INDEX "IX_quran_lemmas_first_word_order_in_mushaf" ON quran_lemmas (first_word_order_in_mushaf)`.
So every persisted lemma must have a *globally distinct* first-occurrence word order.

### Logic bug — multi-STEM-lemma words
The enriched builder (`EnrichedDimensionBuilder.BuildState.Add`) iterates **every STEM segment** of every word and calls `ResolveOrCreateLemma` on each:

```csharp
// EnrichedDimensionBuilder.cs:138-139 (inside the per-segment loop)
segLemmaId = ResolveOrCreateLemma(
    sourceSegment, wordOrder, segRootId, lemmaIndex, lemmaRootLinks, rootLemmaMap, ref nextDimId);
```

When a single word has **two STEM segments with distinct lemma Buckwalter values**, both lemmas are minted fresh in the same pass and both are stamped with `FirstWordOrder = wordOrder` (the word's `quranWordId`). That is a direct violation of the unique index.

### Reproduction against the staged artifact
A direct replay of the builder's lemma-minting rule over the 96 MB artifact shows:

- **483 words** in the Quran have more than one distinct STEM lemma (the `مِنْ مَا`-class compounds, e.g. `2:3:6`, `2:11:9`, `2:14:14`, …).
- The **first** colliding word in word-order is **`2:3:6` (`quranWordId=52`)**, whose two STEM segments carry lemma Buckwalter `min` and `maA`. Both would be minted with `FirstWordOrder=52`. This is exactly COPY line ~35 (≈ the 35th lemma row in insert order), matching the Postgres error.
- The enriched builder would mint **4,832** distinct lemma dimensions total; only **one** word-order (`52`) collides in this dataset — but uniqueness is violated, so the COPY aborts.

### Why the legacy path is unaffected
The legacy assembler (`MorphologyAssembler`) resolves **at most one lemma per word** — the word-level QUL lemma (`qulLemma`), keyed on the word's location (lines 99–152). Per-segment lemma resolution is a separate, *non-minting* pass (`ResolveLemmaId`, line 422) that only looks lemmas up against the already-minted dimension set; it never assigns a new `FirstWordOrder`. Consequently each lemma's `FirstWordOrder` is globally distinct by construction. Legacy regression tests: 35/35 PASS.

### Why Phase 1 tests did not catch this
- The dry validator (`EnrichedMorphologyDryValidator`) asserts dimension-build output shape and the plan's §7 gates, but it does **not** model the DB unique index on `first_word_order_in_mushaf`; it has no concept of uniqueness across lemma rows.
- The writer integration test (`EnrichedMorphologyWriterIntegrationTests`) uses a **5-word synthetic fixture where every word has exactly one STEM segment** (`EnrichedMorphologyWriterIntegrationTests.cs:46-60`), so the multi-STEM-lemma collision is structurally impossible in the fixture. This is a fixture-coverage gap.

### Files / symbols implicated
- **Bug site:** `Backend/infrastructure/QuranDashboard.Infrastructure/Files/Quran/DataPipelines/Words/MorphologyImporting/Enriched/EnrichedDimensionBuilder.cs`
  - `BuildState.Add` (lines 85–186), specifically the per-STEM-segment lemma-minting at lines 138–139
  - `ResolveOrCreateLemma` (lines 299–337) — mints a new `LemmaDimensionEntry` with `FirstWordOrder = wordOrder` regardless of whether another lemma was already minted for the same `wordOrder` this pass
- **Failure site:** `Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/DataPipelines/Quran/Words/MorphologyImporting/MorphologyBulkCopier.cs:76` (`CopyLemmasAsync` binary-import)
- **Index:** migration `20260616095937_AddQuranNavigationMetadata` (and its successors) declare the unique index on `quran_lemmas.first_word_order_in_mushaf`
- **Reference (correct) design:** `MorphologyAssembler.ResolveLemmaId` (lines 422–501) — lookup-only per segment, never mints by segment lemma
- **Coverage gap:** `Backend/tests/QuranDashboard.Tests/Quran/WordsMorphologyEnriched/EnrichedMorphologyWriterIntegrationTests.cs` fixture (single-STEM words only)

### Recommended fix direction (for the next phase — NOT applied here)
Decide, per multi-STEM-lemma word, **a single head lemma** for word-level dimension minting (mirroring the legacy word-level-QUL-lemma rule), and treat secondary STEM lemma Buckwalter values as **per-segment references resolved against the already-minted lemma set**, never as fresh dimension mints. This preserves value-based identity (no QUL location join) while honoring the unique-index constraint. This must be implemented and reviewed as code work in a follow-up; Phase 2A is verification-only and made no code changes.

## 10. Conclusion and next-step recommendation

Phase 2A **did not pass**: the enriched import pathway contains a real Phase 1 logic bug that the dry validator and the unit/integration fixtures do not cover. The bug is narrow and well-localized (`EnrichedDimensionBuilder` per-STEM-lemma minting vs. the pre-existing `UNIQUE` index on `quran_lemmas.first_word_order_in_mushaf`), and the legacy pathway is unaffected.

**Recommended next action (out of Phase 2A scope):** open a remediation task under Feature 020 that (a) restricts enriched lemma dimension minting to a single head lemma per word (with secondary STEM lemmas resolved lookup-only against the minted set, mirroring `MorphologyAssembler.ResolveLemmaId`), (b) extends `EnrichedMorphologyWriterIntegrationTests` with a multi-STEM-lemma fixture (e.g. a `2:3:6`-shaped compound), and (c) optionally extends the dry validator to assert lemma `FirstWordOrder` uniqueness so this class of defect is caught before touching the DB. After remediation, re-run Phase 2A from step 7 (the DB is already in the correct post-foundation, pre-morphology state).
