# Abwab Quran Ayah Linking — Backend & Database Architecture Report

**Scope:** proposed Backend/database architecture for the Linking behaviour now proven by the
implemented Frontend V2 prototype. Ayah linking only.

**Purpose:** this report is the input from which an implementation plan will later be written. It is
detailed enough that, once approved, the plan can be produced without another exploratory audit.

**Method:** source-code audit of the current repository. Nothing was implemented, no production code
was modified, no migration/API/test was created, no Frontend file was touched, nothing was committed.

**Authority order used**
1. `docs/abwab-linking-frontend-v2-current-state-report.md` (the product reference).
2. Current Backend code and the applicable Backend architecture authorities.
3. Current Frontend Linking contracts, only where needed to understand implemented product behaviour.

Where an instruction in the brief assumed an existing Backend capability that does not exist, this
report says so plainly rather than designing against a fiction. There are two such cases: **there is
no ChangeSet/Restore audit architecture** (§B.4) and **there is no Quran data/import version marker**
(§B.6).

## B. What exists — the six facts that shape this design

### B.1 Abwab Door model

[`AbwabDoor`](Backend/domain/QuranDashboard.Domain/Abwab/AbwabDoor.cs) — `Id`, `SectionId` (NOT
NULL), `ParentId`, `Name`, `Description`, `RepresentativeAyahText` (**free text, explicitly never an
FK or a verified Quran reference**), `OrderValue`, `GlobalOrderValue`, the eight audit columns, and
`Version` (`xmin`).

Doors nest without limit; archive is a soft-delete claiming a subtree; restore returns exactly what
that archive claimed. A door is "live" iff `deleted_at IS NULL`. The tree read exposes archived doors
flagged `IsArchived`; the frontend Door picker consumes `snapshot.liveRoots` only.

**`RepresentativeAyahText` is the only Quran-adjacent field on a Door today, and it is deliberately
unverified free text.** Linking is therefore the first real Door→Quran relation in the system.

### B.2 Audit columns exist but are never populated

`created_by`, `updated_by`, `approved_by`, `deleted_by` are mapped on every Abwab entity. A
repository-wide grep for any assignment to `CreatedBy`/`UpdatedBy` outside generated migration
snapshots returns **nothing** — every Abwab write leaves them NULL.

The actor's internal id *is* available: `AuthorizationState(UserId, Status, IsOwner, PermissionCodes)`
is resolved per request from `access_users`
([AuthorizationStateResolver.cs:26-48](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/Reads/Access/AuthorizationStateResolver.cs:26)).
`ICurrentUser` exposes only the Logto `Sub` string. Linking needs the internal `UserId`, so the
Application seam it consumes must be `IAuthorizationStateResolver`/an equivalent, not `ICurrentUser`.

### B.3 Authorization

- `[RequirePermission(code)]` → `PermissionAuthorizationHandler`: succeeds if
  `state.IsOwner || state.PermissionCodes.Contains(code)` — **Owner bypasses every permission check**.
- `[RequireOwner]` → `OwnerAuthorizationHandler`.
- Rejections: `401` challenge, `403` forbid (with four distinguished reasons), `503` when the
  authorization infrastructure is unavailable.
- **`AbwabPermissionCatalogue` is the sole allowlist for `[RequirePermission]`.** Both the runtime
  handler ([PermissionAuthorizationHandler.cs:20](Backend/api/QuranDashboard.Api/Authorization/Permissions/PermissionAuthorizationHandler.cs:20))
  and the startup validator ([UnsafeEndpointMetadataValidator.cs:93](Backend/api/QuranDashboard.Api/Authorization/Validation/UnsafeEndpointMetadataValidator.cs:93))
  check membership in that one list.
- That catalogue's static constructor asserts exactly 19 codes with `DisplayOrder` = 1..19 and
  exactly 5 groups, and `AbwabPermissionCatalogueTests` asserts `HaveCount(19)`. Adding a `linking.*`
  family therefore is **not** a matter of appending entries; it requires a combined-catalogue seam.
- `PermissionCatalogueSynchronizer` writes the code catalogue into `access_permissions` at boot
  (disabled in Production; staged via the AccessAdmin CLI).

### B.4 There is no ChangeSet / Restore audit architecture

The brief asks how Linking writes should "fit the existing Abwab Audit/ChangeSet/Restore
architecture". **That architecture does not exist.** A repository-wide search for `ChangeSet` returns
nothing. What exists is:

1. **`access_audit_events`** — an append-only audit table for *access administration only*
   ([AccessAuditEvent.cs](Backend/domain/QuranDashboard.Domain/Access/AccessAuditEvent.cs)):
   `occurred_at`, `action_type`, `actor_type`, `actor_user_id`, `target_user_id`,
   `actor_snapshot`/`target_snapshot`/`before_state`/`after_state`/`metadata` as `jsonb`,
   `permission_code`, `reason`. Append-only is enforced in `SaveChanges` itself
   ([QuranDashboardDbContext.cs](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/QuranDashboardDbContext.cs) —
   `EnsureAuditEventsAreAppendOnly`), plus two `CHECK` constraints validating jsonb object-ness and a
   numeric `metadata.schemaVersion`, plus a schema-drift preflight
   ([AuthorizationSchemaRequirements.cs:89](Backend/infrastructure/QuranDashboard.Infrastructure/Access/AuthorizationSchemaRequirements.cs:89)).
   Written through `IAccessAuditAppender` ([AccessAuditAppender.cs](Backend/infrastructure/QuranDashboard.Infrastructure/Access/AccessAuditAppender.cs)),
   which enlists in the caller's `DbContext` so the audit row commits in the same transaction.
2. **Abwab soft-delete + restore** — `deleted_at`/`deleted_by` on the row, and
   `abwab.doors.restore`. This is state restoration, not audit replay.
3. **No Abwab write emits an audit event.** `IAccessAuditAppender` has exactly two consumers, both in
   `Persistence/Writes/Access/`.

This is a fact the plan must build on, not a gap this report invents around.

### B.5 Quran/Words read models — the exact identity availability

The five automatic source families are backed by read-only EF readers under
`Persistence/Reads/Quran/Words/**`. Their ayah-match DTOs:

| DTO | Canonical word id? | Fields |
| --- | --- | --- |
| `UniqueWordAyahMatchDto` | **Yes** | `AyahId, VerseKey, SurahNameArabic, AyahNumber, PageNumber, MatchedQuranWordIds, Words[AyahWordForHighlightDto(QuranWordId, TextUthmani, IsAyahMarker)]` |
| `WordTypeAyahMatchDto` | **Yes** | `VerseKey, SurahNumber, AyahNumber, PageNumber, MatchedWordPositions, MatchedWordIds, Words[AyahWordForHighlightDto]` |
| `RootAyahMatchDto` | **No** | `AyahId, VerseKey, SurahNameArabic, PageNumber, Words[RootAyahWordDto(TextUthmani, IsMatched)]` |
| `LemmaAyahMatchDto` | **No** | identical shape |
| `StemAyahMatchDto` | **No** | identical shape |

**The missing ids are a projection choice, not a data limitation.** The shared hydration helper
already loads `QuranWordId` for every word:
[`AyahWordHydration.AyahWordRow(AyahId, QuranWordId, WordNumber, PageNumber, TextUthmani, IsAyahMarker)`](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/Reads/Quran/Words/AyahWordHydration.cs) —
Root/Lemma/Stem simply drop it when projecting their DTO. Surfacing canonical word ids for those three
families costs one extra `int` per word in the projection and **zero extra queries**.

Other relevant facts:

- Detail page size is **100** for all five families
  (`ROOT_DETAIL_PAGE_SIZE`, `LEMMA_DETAIL_PAGE_SIZE`, `STEM_DETAIL_PAGE_SIZE`,
  `DEFAULT_AYAH_PAGE_SIZE`, `WORD_TYPES_DETAIL_PAGE_SIZE`).
- Root/Lemma/Stem ayah reads are **bounded to 4 commands per page** (existence check, distinct-ayah
  count, page metadata, matched rows) plus one hydration query
  ([EfRootsReader.cs:114-190](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/Reads/Quran/Words/Roots/EfRootsReader.cs:114)).
  There is no N+1.
- `AyahWordHydration` **excludes ayah markers by default** (`!w.IsAyahMarker`; since Phase 3 the filter
  is a parameter defaulting to exclusion), which is why Root/Lemma/Stem **and Word Type** results carry
  no marker tokens at all. Unique Word keeps its markers through its own reader
  ([EfUniqueWordsReader.cs:227](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/Reads/Quran/Words/EfUniqueWordsReader.cs:227)),
  never through this hydration path.
- `quran_words.location` carries a **UNIQUE index**
  ([QuranWordConfiguration.cs:85](Backend/infrastructure/QuranDashboard.Infrastructure/Persistence/Configurations/Quran/QuranWordConfiguration.cs:85)) —
  a `wordLocation → quran_word_id` resolution is one indexed lookup, batchable with `= ANY(...)`.
- `quran_words` also has `IX_quran_words_readable_surah_ayah_word` filtered `is_ayah_marker = false`
  and an FK index on `ayah_id`. `quran_word_morphology` has indexes on `root_id`, `lemma_id`,
  `stem_id`.
- `quran_ayahs` carries `VerseKey`, `PageFrom`, `PageTo`, `WordsCountSource`/`WordsCountReal` — the
  authoritative metadata the manual Mushaf path already depends on.

### B.6 Caching architecture — backend

Two distinct, deliberately different patterns coexist.

**Pattern 1 — Quran/Words reads: expiration-only, no invalidation.**
Decorator readers (`CachedRootsReader`, `CachedLemmasReader`, `CachedStemsReader`,
`CachedUniqueWordsReader`, `CachedWordTypesReader`, and the seven `CachedMushaf*` readers) wrap the
`Ef*Reader` behind the same interface and use one shared `IMemoryCache`. A grep for any
invalidation/`Remove(` under `Caching/Quran/` returns **nothing**.

| Entry family | Expiry |
| --- | --- |
| Roots/Lemmas/Stems `SummaryAll` | **none — cached for the process lifetime** (`RootsCacheEntryOptions.SummaryAll() => new()`) |
| Roots/Lemmas/Stems paged/whole detail | 30 min sliding |
| Unique Words list | 15 min absolute · detail 30 min sliding |
| Word Types table/rows | 30 min absolute · detail 15 min absolute |
| Mushaf detail | 30 min sliding · catalogs 12 h absolute |

Consequence: **a Quran/morphology reseed is not reflected in the whole-summary caches until the API
process restarts.** That is the current accepted posture, not an oversight this report should silently
change.

**Pattern 2 — Abwab reads: generation-stamped, write-invalidated, no expiry.**
`AbwabCacheGeneration` is one singleton holding a per-process boot `Guid` plus one counter per
resource; every write bumps it through an `Invalidating*Writer` decorator in a `finally`; readers
capture the generation *before* loading and stamp the entry; an entry is served only if its stamp
still equals the current generation. The ETag is the boot id + counter — an opaque server generation,
never row data.

**Stampede protection:** [`CacheLoadGate`](Backend/infrastructure/QuranDashboard.Infrastructure/Caching/CacheLoadGate.cs)
is a single-flight semaphore keyed per cache key. Its own comment is a binding constraint: *"Gates are
held per key for the process lifetime, so the key space must stay bounded (the finite lemma/stem
catalogue); do not reuse this for unbounded or caller-supplied keys without adding eviction."*

**Memory-cache configuration:** `services.AddMemoryCache()` is called three times against the same
singleton (`AbwabDependencyInjection.cs:12`, `AccessDependencyInjection.cs:28`,
`MushafReaderDependencyInjection.cs:14`) with **no `SizeLimit` and no entry `Size`**. The process
memory cache is currently unbounded.

**No data/import version marker exists.** There is no `import_run`, `data_version`, or
`quran_data_generation` table anywhere. The only in-repo `schemaVersion` is the one inside
`access_audit_events.metadata`.

**No response compression is configured** — a grep for `AddResponseCompression`/`ResponseCompression`
across `api/` returns nothing.

**Single-instance constraint.** `Backend/README.md` §Deployment states it, load-bearing: the Abwab
cache generation is per-process memory, so a second Railway instance would
serve stale bodies behind fresh-looking `304`s. **Do not scale horizontally until that generation is
shared.** Any Linking cache design must not make this worse and must not silently assume it is fixed.

### B.7 Caching architecture — frontend

[`ApiResponseCache`](Frontend/quran-dashboard-ui/src/app/core/caching/api-response-cache.ts) — an
in-memory `Map` of whole `ApiResponse` objects, **max 48 entries**, LRU-by-recency eviction, in-flight
single-flight dedup, **no expiry**, root-provided so it lives for the browser session. Six instances:
`MushafReaderCache`, `RootsCache`, `LemmasCache`, `StemsCache`, `UniqueWordsCache`, `WordTypesCache`.

Critical current fact: **the Linking source resolvers bypass all of these.** They call
`RootsApi`/`LemmasApi`/`StemsApi`/`UniqueWordsApi`/`WordTypesApi` directly
(`root-linking-source.resolver.ts:4`), so reopening the same source in the Linking editor re-issues
every page request. Only the manual Mushaf path reuses a frontend cache (`MushafReaderCache`, via
`ManualMushafAyahReader`).

# PART II — RECOMMENDED ARCHITECTURE

## 1. Locked scope: Ayah linking only

No Surah linking table, command, or abstraction is proposed. Every durable link grain in §17 is an
`ayah_id`. Surah-level structure is available for free later by aggregating `quran_ayahs.surah_number`
in a read; nothing in the write model needs to anticipate it.

## 2. Typed source descriptor representation

**Recommendation: a three-part hybrid — typed FK columns for referential integrity, one bounded
`jsonb` scope for the non-referential discriminators, and one canonical `source_identity` text column
that carries uniqueness and the cache key.**

Reducing every source to a string is rejected outright (the brief forbids it, and it would make
"which sources reference root 412?" unanswerable). Fully flattening Word Type into sparse columns is
also rejected: it alone contributes eleven discriminators
(`selectionKind`, `tashkeelWordId`, `contextCode`, `case`, `tense`, `voice`, `scope.type`,
`scope.childCode`, `scope.case`, `scope.tense`, `scope.voice`), producing a table where most columns
are NULL for most rows.

| Part | Columns | Why |
| --- | --- | --- |
| **Kind** | `source_kind` text, CHECK in (`unique_word`,`root`,`lemma`,`stem`,`word_type`,`manual_mushaf_ayahs`) | discriminant |
| **Typed references** | `root_id`, `lemma_id`, `stem_id`, `unique_simple_word_id`, `unique_tashkeel_word_id`, `word_type_tashkeel_word_id` — all nullable, all real FKs | integrity + "find every source touching root X" without jsonb querying |
| **Bounded scope** | `scope jsonb NOT NULL` with `CHECK (jsonb_typeof(scope) = 'object' AND jsonb_typeof(scope->'schemaVersion') = 'number')` | `mode`, `typeCode`, `selectionKind`, `contextCode`, `case`, `tense`, `voice`, `scope{...}` — high-arity, low-cardinality, never joined |
| **Canonical identity** | `source_identity text NOT NULL` | deterministic serialization; carries every uniqueness constraint and the cache key |
| **Display snapshot** | `label text NOT NULL` | human-readable value at capture time; **never identity** |

Two notes the plan must carry:

- **Unique Word's `wordId` targets two different tables** depending on `mode`
  (`quran_words_unique_simple` vs `quran_words_unique_tashkeel`), which is why two nullable FK columns
  are proposed rather than one. A single untyped `unique_word_id` would have no enforceable FK. A
  `CHECK` pins exactly one of the pair non-null when `source_kind = 'unique_word'`.
- **`source_identity` must be produced by one shared canonicalizer** whose output is byte-identical to
  the frontend's `linkingSourceKey`
  ([linking-source-key.ts](Frontend/quran-dashboard-ui/src/app/features/linking/utils/linking-source-key.ts)) —
  `|`-joined, `encodeURIComponent`-escaped parts, manual sources keyed by the numerically ordered
  de-duplicated verse-key set only. Divergence between the two implementations would silently split
  the cache and break workspace idempotency; the plan should treat cross-checking them as a first-class
  requirement.

The `jsonb` + `CHECK` + `schemaVersion` shape is not novel here — it is exactly what
`access_audit_events` already does (§B.4), including a schema-drift preflight to detect a dropped
constraint.

## 3. Complete source resolution

**Recommendation: one Linking-owned resolution boundary that returns the complete validated set in a
single response, behind a conditional GET.**

```
GET /api/linking/sources/resolve            (Owner/permission-gated, POST if the scope
                                             exceeds a sane query-string length)
  → ApiResponse<LinkingResolvedSourceDto>
```

```
LinkingResolvedSourceDto
  sourceIdentity        : string        // echo of the canonical identity
  resolvedAtUtc         : timestamptz
  totalAyahCount        : int
  ayahs[]               : LinkingResolvedAyahDto
      ayahId            : int
      verseKey          : string
      surahNumber       : short
      ayahNumber         : short
      surahNameArabic   : string
      pageFrom/pageTo   : short
      words[]           : LinkingResolvedWordDto
          quranWordId   : int           // CANONICAL, for every family
          wordNumber    : short
          textUthmani   : string
          isAyahMarker  : bool
      matchedQuranWordIds : int[]       // CANONICAL, for every family
```

**Why one response, not chunking or streaming.** The Frontend's own contract already publishes a
source only after full success — `loadCompletePagedSource` emits once, after every page validates
([complete-paged-source.loader.ts](Frontend/quran-dashboard-ui/src/app/features/linking/data-access/complete-paged-source.loader.ts)),
and `LinkingSourceSetCoordinator` publishes a merged result only when every member succeeds under one
generation. Chunking would therefore add framing complexity while the consumer still buffers the whole
set before rendering. Streaming is a genuine option only if a measured payload proves unacceptable;
see §20 for the sizes, which do not currently justify it.

**Required companions**

1. **Conditional GET.** Serve `ETag` = boot-id + linking-source-cache generation + `source_identity`,
   with `Cache-Control: no-store`, exactly per `API_GUIDELINES.md` §Conditional GETs. Reopening the
   same source in a later session then costs a `304` rather than a multi-megabyte body. This is the
   single highest-value addition for the "do not repeat expensive work" requirement.
2. **Response compression.** None is configured today (§B.6). Arabic Uthmani text compresses
   extremely well; enabling br/gzip for this route is close to mandatory before shipping a 2,000-ayah
   response. The plan must include verifying it rather than assuming Railway's edge does it.
3. **A hard ceiling.** The largest plausible source is bounded by the Quran itself (6,236 ayahs). A
   configured `MaxResolvedAyahs` guard that returns a controlled `400`/`413` rather than an unbounded
   body is cheap insurance against a future scope that matches nearly everything.

**What must NOT remain:** the Linking client walking `ceil(total/100)` ordinary explorer pages. That
workaround is explicitly retired by this boundary.

**Ordinary explorer pagination is untouched.** `/api/words/{roots|lemmas|stems}/{id}/ayahs?page=N&pageSize=100`
and friends keep their contract, their cache keys, and their 100-row page size. The Linking boundary is
a *second* consumer of the same underlying readers, not a replacement.

**Implementation shape.** A new `ILinkingSourceResolutionReader` in Abstractions, with an
`EfLinkingSourceResolutionReader` in `Persistence/Reads/Linking/` that dispatches by `source_kind` to
per-family queries. Those queries should reuse the existing predicate bases rather than re-deriving
them — `WordMorphologies.Where(m => m.RootId == id)`, the shared `BaseRowsSql` occurrence base for
Word Type, `AyahWordHydration` for word projection — with the page `Skip/Take` removed and
`AyahWordHydration`'s marker filter made a parameter. Only the Linking Unique Word and Manual Mushaf
families pass `true`; Root/Lemma/Stem **and Word Type** keep their current marker-free shape, matching
their explorers (see `specs/001-abwab-linking-backend/contracts/linking-sources-api.md` for the
normative per-family marker rule). Expect the reader to exceed the 400-line soft
threshold and need a partial split by family, matching `EfWordTypesReader`'s existing precedent.

## 4. Caching (mandatory) — three separate concerns

The brief is right that these are three different things. Naming them apart is half the design.

### 4.1 Backend reusable source-truth cache — **required**

**Recommendation: a dedicated, size-limited in-process `IMemoryCache` holding a *compact canonical*
resolved source, wrapped by a `CachedLinkingSourceResolutionReader` decorator. No Redis.**

| Aspect | Recommendation |
| --- | --- |
| **Key** | `linking:source:v1:{source_kind}:{sha256(canonical scope)[..16]}` — derived **only** from the typed source descriptor. Follow `WordTypesCacheKeys.HashParts`' delimiter-escaping so a free-text part cannot collide with a different scope combination. |
| **What is in the key** | Unique Word `mode`+id; Root id; Lemma id + `typeCode`; Stem id + `typeCode`; complete Word Type selection kind + dimension id + all five scope fields; manual source's ordered verse-key set. |
| **What is NEVER in the key or the value** | ayah inclusion/exclusion, selected words, descriptions, checked workspace membership, selected Door, user id. The cached value is Quran/source truth only. |
| **Value shape** | **Compact, not the wire DTO** — see below. |
| **Expiration** | 30 min sliding, matching the existing Words detail convention. Not "no expiry": a source result is a caller-shaped key space, unlike `SummaryAll`. |
| **Invalidation** | None write-driven — nothing in the API mutates Quran/morphology data. Bounded staleness comes from the sliding window; a reseed is picked up on restart, exactly like every existing Quran cache. |
| **Stampede** | **Do not reuse `CacheLoadGate`** — its own comment forbids caller-supplied key spaces, and Word Type scopes are combinatorial. Cache a `Task<T>`/`AsyncLazy<T>` in the entry instead, so the entry itself is the gate and eviction is automatic. |
| **Size** | A **dedicated** `MemoryCache` instance with `SizeLimit` and a per-entry `Size` ≈ ayah count. It must not be the shared `IMemoryCache`: setting `SizeLimit` on that one makes every existing size-less `Set` throw. |

**Cache the compact representation, not the full DTO — this is the memory-critical decision.**

For a 2,000-ayah source (~26,000 words), the wire DTO with Uthmani text costs roughly:
26,000 × (≈80 B of UTF-16 text + ≈26 B string header + ≈50 B record overhead) ≈ **4 MB per entry**.
Fifty warm sources ≈ 200 MB — untenable on a Railway Hobby single instance with an already-unbounded
shared cache.

The compact form stores per ayah: `ayahId:int`, and two `int[]` (`quranWordIds`, `matchedQuranWordIds`)
— ≈ 26,000 × 4 B × 2 ≈ **210 KB per entry**, ~20× smaller. Uthmani text and ayah display metadata are
then hydrated from a **second, shared, highly reusable cache keyed by ayah id**, which is naturally
deduplicated across every source that touches the same ayah (Root X and Lemma Y overlapping on ayah A
share one text entry instead of two copies). That second cache is the one that should be generous, and
it is bounded by the Quran: 6,236 ayahs total.

**Redis: not now.** The current architecture is explicitly single-instance and cannot be scaled
horizontally until the Abwab cache generation is shared (§B.6) — so the usual "two instances need a
shared cache" trigger is already blocked by an earlier constraint. The cached value is derived,
rebuildable, and cheap to recompute. Introduce Redis only when **both** (a) a second instance is
genuinely being added, and (b) measured memory pressure or cold-start cost justifies it. Adding it now
buys nothing and adds an operational dependency to a Hobby deployment.

### 4.2 Frontend short-lived resolved-source cache — **required, cheap**

The Frontend already owns the right primitive and simply is not using it for Linking (§B.7).

**Recommendation: give Linking its own `LinkingSourceCache extends ApiResponseCache`, keyed by
`linking:source:{sourceIdentity}`, and route resolution through it.** That alone fixes:

- reopening the same source's ayah editor in one session → zero network;
- editor → review → back-to-editor round trips → zero network;
- retry after a *client-side* navigation → zero network.

Two adjustments the plan should specify:

- **The 48-entry cap is wrong for this payload.** `ApiResponseCache`'s `DEFAULT_MAX_ENTRIES = 48` was
  sized for small explorer pages. A Linking instance holding 48 complete sources could hold tens of
  megabytes. Give this instance a small cap (≈6–8 sources), which comfortably covers one workspace's
  worth of prepared sources.
- **Keep `MushafReaderCache` reuse for the manual path exactly as it is** — `ManualMushafAyahReader`
  already deduplicates page reads through it, and the manual Mushaf resolution boundary should stay a
  client-side composition of study + page reads unless the backend chooses to serve manual sources
  through the same `/resolve` boundary (see §M-3).

### 4.3 Workspace persistence — **not a cache**

Per-user mutable state in PostgreSQL (§11). It is never populated from either cache, never expires,
and never participates in source-truth invalidation. Stating this explicitly is the point: the three
must not be merged in the implementation plan.

## 5. Per-source ayah contribution

**Recommendation: the durable grain is `(source contribution, ayah)`, never `(door, ayah)`.**

Root X contributing ayah A and Lemma Y contributing ayah A produce **two** rows, each owned by its own
`linking_source_contributions` row, each carrying its own selected words and its own descriptions. A
future Door read aggregates them; the write model never collapses them.

This is the direct durable counterpart of the Frontend invariant already proven in code: merge
deduplicates *display* by `verseKey`, while `createLinkingSourceIntent` derives intents per member from
that member's own reconciled ayahs
([linking-source-intents.ts](Frontend/quran-dashboard-ui/src/app/features/linking/utils/linking-source-intents.ts)).

## 6. Selected words — canonicalization strategy

**Recommendation: `quran_words.id` is the only durable word identity. Nothing else is ever stored.**

Three resolution rules:

1. **Automatic sources → canonical at the read.** Extend the Root/Lemma/Stem resolution projection to
   carry `QuranWordId` and `MatchedQuranWordIds`, which `AyahWordHydration` already loads (§B.5). This
   **eliminates the `presentation-occurrence` identity class entirely** — the Frontend's
   `LinkingWordContribution` union collapses from three arms to one for every automatic family.
2. **Manual Mushaf `wordLocation` → canonical before or at confirmation.** `quran_words.location` is
   UNIQUE, so a batch `WHERE location = ANY(@locations)` resolves an entire manual selection in one
   indexed query. **Recommendation: resolve at *workspace save* time, not only at confirmation** — so
   the workspace itself stores `quran_word_id`, and an invalid coordinate is refused when the user
   saves their word selection rather than surfacing at the end of the flow.
3. **Presentation indexes are never accepted on the wire.** `renderPosition`, array index,
   `wordNumber`, `lineWordOrder`, and Uthmani text are rejected as identity inputs by the API contract.

**Validation every submitted `quran_word_id` must pass, at both workspace save and confirmation:**

| Rule | Check |
| --- | --- |
| exists | row present in `quran_words` |
| non-marker | `is_ayah_marker = false` |
| belongs to the declared ayah | `quran_words.ayah_id = <declared ayah_id>` |
| belongs to that source contribution | the ayah is a member of the source's freshly resolved set, and for an automatic source the word is in that ayah's `matchedQuranWordIds` |

The last rule is the anti-tamper boundary and is the reason confirmation re-resolves the source
(§13). Its cost is one warm-cache lookup.

**Deliberate asymmetry worth stating:** for an **automatic** source the selected words are *derived*
(the ON/OFF preference selects all matched words, and the user never picks individual words —
Frontend §1.5), whereas for a **manual** source they are *authored*. Both land in the same durable
table, but only the manual side needs a per-word user-intent store in the workspace. The automatic
side's workspace stores the boolean preference and materializes the word set at confirmation.

## 7. Per-source / per-ayah descriptions

**Recommendation: first-class rows, one table per side (workspace-mutable and confirmed-durable),
hanging off the `(source contribution, ayah)` grain — never off the ayah.**

A single `description` column is rejected because the requirement is explicitly "one or more".
A `text[]` column is rejected because reorder/edit/delete of one entry becomes a whole-array rewrite
with no stable identity, and because the repo's own precedent for authored child collections
(`abwab_door_aliases`) is a child table.

| Question | Recommendation |
| --- | --- |
| **First-class?** | Yes — own row, own surrogate `id`. |
| **Stable identity** | Surrogate `bigint id`. Not the body text, not the position. |
| **Ordering** | `order_value int NOT NULL`, resequenced `1..N` on every mutation, using the same `Resequence` discipline every Abwab write already follows. `UNIQUE (owner_id, order_value)` is deliberately **not** added, for the same reason `abwab_doors.order_value` has none: renumbering issues one UPDATE per row and a per-statement unique index would transiently violate. |
| **Edit / delete / reorder** | Workspace side: full CRUD, hard delete, `xmin` on the row. Confirmed side: soft delete (`deleted_at`), matching the Abwab convention, so a later "restore" means un-delete. |
| **Bound on count** | **Yes — bound it.** Recommend `CHECK (order_value BETWEEN 1 AND 20)` plus an application guard. Unlimited descriptions on 2,000 ayahs × N sources is an unbounded write surface with no product need behind it. 20 is generous; the number is a product-owner call (§M-1). |
| **Text length** | `varchar(2000)`, `CHECK (btrim(body) <> '')`. Precedent: `access_audit_events.reason` is `HasMaxLength(1024)`; 2,000 suits a linking rationale. |
| **Plain text?** | **Yes — plain text.** No markup, no HTML, no rich text. The system has no sanitization infrastructure and no rendering pipeline for anything else. |
| **Never merged** | Structurally guaranteed: a description's parent is `(contribution, ayah)`. Two sources contributing the same ayah are two different parents. There is no schema path by which they could merge. |
| **Audit/Restore** | See §14 — descriptions participate exactly as any other confirmed child row: soft-deleted with their parent, un-deleted with it, and included in the `after_state` document if an audit event is introduced. |

## 8. Grouped vs independent intent

**Recommendation: a real `linking_units` table between the source contribution and the ayah.**

```
linking_source_contributions   (one per source in one confirmed operation)
   └── linking_units           (one intent unit; ordered)
         └── linking_unit_ayahs (the ayah link grain)
```

| Contribution mode | Units produced |
| --- | --- |
| `automatic` | one unit per included ayah, each with exactly 1 ayah |
| `manual_single` | one unit, 1 ayah |
| `manual_independent` | one unit per included ayah, each with 1 ayah |
| `manual_grouped` | **exactly one** unit containing all N ayahs |

Worked example (the locked invariant):

```
Manual Mushaf, grouped, {A,B}   → contribution#1 → unit#1 { A, B }
Lemma Y,       automatic, {A,C} → contribution#2 → unit#2 { A }, unit#3 { C }

Rows in linking_unit_ayahs: (unit#1,A) (unit#1,B) (unit#2,A) (unit#3,C)
Merged display (a future read): A, B, C — each once
Durable intent: [[A,B]] and [[A],[C]] — never [[A,B,C]], and A is not lost
```

**Alternatives rejected.**
- A `group_id` nullable column on a flat link row: cannot express "these two grouped rows belong to
  different sources" without also storing the source, and makes "one unit" a convention rather than a
  row.
- Inferring grouping from the row count of a contribution: the Frontend already rejects this
  (`effectiveManualLinkShape` derives from the *preference*, not the count), and it makes a grouped
  source that temporarily has one included ayah indistinguishable from an independent one.

**Enforcement.** `contribution_mode = 'automatic'` ⇒ every unit has exactly one ayah. PostgreSQL
cannot express a cross-row cardinality constraint declaratively without a trigger, and this repository
uses **no triggers** anywhere. Recommendation: enforce in the writer, back it with a retained
behaviour test, and add the cheap half declaratively — a `is_grouped boolean NOT NULL` on
`linking_units` with `CHECK` that an automatic contribution's units are never `is_grouped`. Be honest
in the plan that the cardinality half is application-enforced.

## 9. Door ownership

**Recommendation: `linking_operations.door_id` → `abwab_doors.id`, `ON DELETE RESTRICT`, plus a
denormalized `door_id` on `linking_source_contributions` to carry the door-scoped uniqueness index.**

No change to the Abwab hierarchy is proposed. Notes:

- **Doors are soft-deleted.** An FK cannot express "must be live" — liveness is
  `deleted_at IS NULL`, checked by the writer at confirmation (the same way
  `MockLinkingCommandPort` validates against `liveRoots` today). Archiving a door with links must
  **not** cascade into linking rows: relations already set that precedent — *"Relations are attached
  to doors, not to structure — and no door write touches them"*, as implemented by the Abwab writers, so
  restore has something to bring back. Linking should behave identically: archiving a door hides its
  links from a future read by joining on the door's liveness, and restoring brings them straight back.
- **`RESTRICT`, not `CASCADE`.** Every Abwab FK in the repo is `OnDelete(DeleteBehavior.Restrict)`;
  nothing is hard-deleted.
- **Section is not denormalized onto linking rows.** A door's section can change (`MoveAsync`
  cascades it), so storing it would be a second thing to maintain with no read that needs it today.

## 10. Provenance vs materialized links — the historical-integrity rule

**Recommendation: materialize the outcome, retain the descriptor as provenance, and never re-derive.**

This matters most for Root/Lemma/Stem/Word Type: those sets are *computed from morphology data*. If a
later morphology reseed changes which ayahs match root X, a confirmed link must not silently change.

| Materialized at confirmation (immutable Quran truth) | Retained as provenance (historical, never re-executed) |
| --- | --- |
| `door_id` | `source_kind` |
| `ayah_id` per unit-ayah | typed FK ids (`root_id`, `lemma_id`, …) |
| `quran_word_id` per selected word | `scope` jsonb (mode / typeCode / full Word Type scope) |
| description bodies + order | `source_identity` |
| unit grouping and unit order | `label` display snapshot |
| contribution order | `resolved_ayah_count` at confirmation |
| actor + timestamp | `resolved_at_utc` |

Consequences to state in the plan:

- A confirmed contribution's `root_id` FK answers *"this link was reached via root X"*. It is **not**
  a live membership assertion and must never be re-resolved to reconstruct the link set.
- `resolved_ayah_count` alongside the actual materialized row count makes drift **detectable** later
  (a future "this source now matches 14 ayahs but you linked 12" advisory) without making it
  automatic.
- The `label` snapshot is display only. The Frontend already treats descriptor labels this way; the
  Backend must too.

## 11. Workspace persistence

**Recommendation: a real per-user server-side workspace, structurally mirroring the Frontend's proven
state model, kept strictly separate from confirmed links.**

The Frontend's persisted shape is already exactly right and should be transposed, not redesigned:
ordered prepared sources; per-source `LinkingSelection` (`all-except` | `only` + override verse set);
`automaticWordMatchesEnabled` for automatic; `wordLocationsByVerseKey` + `linkShape` for manual;
`lastResolvedCount` marked stale on load.

**Server-side, in the workspace:**

| Concept | Where |
| --- | --- |
| workspace owner | `linking_workspaces.user_id` UNIQUE → `access_users.id` |
| ordered prepared sources | `linking_workspace_sources.order_value` |
| typed source descriptor | the §2 hybrid, on `linking_workspace_sources` |
| ayah inclusion/exclusion | `inclusion_mode` + `linking_workspace_source_ayah_overrides` child rows |
| automatic-word preference | `automatic_word_matches_enabled boolean` (NULL for manual) |
| manual selected words | `linking_workspace_source_words` — **already canonical `quran_word_id`** (§6) |
| manual grouped/independent | `manual_link_shape` (NULL for automatic) |
| manual verse set | `linking_workspace_source_manual_ayahs` (also the relational truth behind the manual `source_identity`) |
| per-source/per-ayah descriptions | `linking_workspace_source_descriptions` |
| revision/concurrency | `xmin` on `linking_workspaces` and on `linking_workspace_sources` |
| resolved-count metadata | `last_resolved_count` + `last_resolved_at_utc`, both advisory |

**Stays client-side (unchanged from the prototype):** checked sources for the current operation,
active modal/surface, focus, search query, CDK viewport position, review position, loading/error
state, and the selected Door before confirmation.

On "checked sources": the Frontend already treats this as transient and resets it on hydration, with a
stated rationale — persisting it could make a later click link stale, forgotten membership. **Keep it
client-side.** There is no strong reason to move it, and moving it would create a second, weaker
notion of "an operation" competing with `linking_operations`.

**Workspace persistence and confirmed links must not become one model.** They differ on every axis:
mutable vs immutable, per-user vs per-Door, hard-delete vs soft-delete, descriptor-as-live-intent vs
descriptor-as-history. They share only the *shape* of the source descriptor, which should be a shared
value-object mapping, not a shared table. The plan should explicitly forbid a "status column"
unification.

**Concurrency.** `xmin` on `linking_workspaces` gives a single whole-workspace token, matching the
Frontend's existing `durableWorkspaceRevision`. Per-source `xmin` additionally allows editing two
sources concurrently without a false conflict. Recommend both, with the whole-workspace token used for
"reorder / add / remove" and the per-source token for "edit this source's configuration".
Last-writer-wins is **not** acceptable server-side; a stale token is a `409`, exactly as every Abwab
write already answers.

## 12. Idempotency and duplicate linking

**Recommendation: three distinct uniqueness boundaries. `(door_id, ayah_id)` alone is explicitly
insufficient and is not used.**

| Scenario | Recommended behaviour |
| --- | --- |
| **Same source confirmed twice against the same Door** | Refused. `UNIQUE (door_id, source_identity) WHERE deleted_at IS NULL` on `linking_source_contributions` → `409`. "This source is already linked to this Door; edit that contribution instead." |
| **Same ayah reaches a Door from two different sources** | **Allowed and preserved.** Two contributions, two unit-ayah rows. This is the §5 requirement. |
| **Same ayah twice within one source** | Impossible. `UNIQUE (source_contribution_id, ayah_id)` on `linking_unit_ayahs` (see the denormalization note in §17). |
| **Same selected word from two sources** | Allowed — two rows under two different unit-ayahs. `UNIQUE (unit_ayah_id, quran_word_id)` prevents only the intra-contribution duplicate. |
| **Grouped manual intent overlapping an automatic intent** | Allowed, structurally independent. The grouped unit and the automatic singletons are separate `linking_units` rows under separate contributions. |
| **User later modifies an existing source contribution** | An **update** of the live contribution under its `xmin`, not a second insert. Adding/removing an ayah, changing selected words, or editing descriptions all operate on the existing contribution. Changing the *descriptor* produces a different `source_identity` and is therefore a different contribution — the user removes the old one and confirms the new one. |
| **Network retry of one confirmation** | `UNIQUE (idempotency_key)` on `linking_operations`, key supplied by the client per confirmation attempt. A replay returns the original result rather than a `409` or a duplicate. |

**Why not `(door_id, ayah_id)`:** it would make the two-sources-one-ayah case (§5) unrepresentable,
destroy per-source descriptions and per-source word selections, and collapse the grouped/independent
distinction. It is precisely the constraint the product forbids.

## 13. Confirmation / write transaction boundary

**One atomic Application command.** Conceptual shape only — no implementation.

```
ConfirmLinkingOperationCommand
  idempotencyKey : guid
  doorId         : int
  sources[]      : { sourceDescriptor, contributionMode,
                     units[] : { ayahIds[] },
                     ayahWords    : { ayahId → quranWordId[] },
                     ayahDescriptions : { ayahId → [ {order, body} ] } }
```

Ordered validation, all before any write:

| # | Step | Failure |
| --- | --- | --- |
| 1 | **Idempotency** — existing `linking_operations.idempotency_key`? | return the original result, `200` |
| 2 | **Actor** — resolve `AuthorizationState`; Owner (or `linking.*` permission per §15) | `401` / `403` |
| 3 | **Door** — exists **and** `deleted_at IS NULL` | `404` / `400` "door no longer available" |
| 4 | **Descriptors** — each parses to a valid typed descriptor; referenced root/lemma/stem/word ids exist | `400` |
| 5 | **Source membership** — re-resolve each source through the §4.1 cached boundary; every submitted `ayah_id` must be a member | `400`, naming the offending source |
| 6 | **Ayahs** — exist in `quran_ayahs`; no duplicate within a contribution | `400` |
| 7 | **Words** — the four rules of §6, batched per contribution | `400` |
| 8 | **Grouped intent** — mode/unit cardinality consistent (§8) | `400` |
| 9 | **Descriptions** — count ≤ bound, body length, non-blank, contiguous order | `400` |
| 10 | **Idempotency boundary** — no live contribution already exists for `(door_id, source_identity)` | `409` |

Then, inside **one explicit transaction**:

```
INSERT linking_operations
  for each source (in submitted order):
     INSERT linking_source_contributions
       for each unit:
          INSERT linking_units
            for each ayah:
               INSERT linking_unit_ayahs
                 INSERT linking_unit_ayah_words   (batch)
                 INSERT linking_unit_ayah_descriptions (batch)
  (optionally) APPEND linking audit event — same transaction, see §14
COMMIT
```

- **Explicit transaction is mandatory** — this spans many `SaveChanges`-worth of inserts, and EF's
  implicit transaction covers one call only.
- **Exception translation is mandatory** — a `23505` from the `(door_id, source_identity)` index must
  become a plain Abstractions exception mapped to `409`, and any `DbUpdateConcurrencyException` must
  become a stale-token `409`. An untranslated save reaches the global handler as a `500`, which is the
  exact defect the Abwab writer implementations avoid.
- **Failure behaviour: all-or-nothing.** One rejected source fails the whole operation, matching both
  the Abwab bulk-write precedent and the Frontend's own atomic publication.
- **Optimistic concurrency** applies to *update* paths (editing a live contribution) via that
  contribution's `xmin`. A fresh confirmation is an insert and needs no token.
- **Cache impact: none.** Confirmation writes no Quran data, so no source-resolution entry is
  invalidated. This is a genuine simplification versus the Abwab write path and should be stated so
  nobody adds a pointless invalidating decorator.

## 14. Audit / Restore integration

**Recommendation: do not invent a second audit system — because there is no first one to extend
(§B.4). Land in two deliberate stages.**

**Stage 1 (with the first Linking write, required):**

1. **Populate the audit columns Abwab leaves NULL.** `created_by`, `updated_by`, `deleted_by` on every
   Linking table, stamped from `AuthorizationState.UserId`. Linking is a per-user authored artifact;
   unattributed authorship is not acceptable here even though Abwab tolerates it today.
2. **Soft delete on all confirmed tables** (`deleted_at`, `deleted_by`), with partial unique indexes
   filtered `deleted_at IS NULL`. "Restore" then means un-deleting a contribution and its children —
   the same mechanism `abwab.doors.restore` uses, requiring no new machinery.
3. **Claim-scoped restore.** Reuse the Abwab rule verbatim: an un-delete restores exactly the rows the
   matching delete claimed, matched on that delete's own `deleted_at` timestamp. Do **not** widen it to
   "all deleted children", which would resurrect rows deleted deliberately earlier.

**Stage 2 (only when a product requirement for history exists):** a `linking_audit_events` table
following the `access_audit_events` precedent **exactly** — append-only enforced in
`SaveChanges`, `jsonb` `before_state`/`after_state`/`metadata` with a numeric `schemaVersion`, the two
`CHECK` constraints, an appender that enlists in the caller's `DbContext` so the event commits in the
same transaction, and a schema-drift preflight entry. Reusing that shape is what "do not invent a
second parallel audit system" means in this repository.

**What would become audited domain state:** the confirmed side only — operations, contributions,
units, unit-ayahs, words, descriptions. The workspace is a per-user draft; auditing every checkbox is
noise.

**How source-contribution changes would appear:** one event per confirmation/edit/removal, whose
`after_state` is the complete contribution document (descriptor + units + ayahs + words +
descriptions). Because the contribution is the natural aggregate, one document per event is both the
change unit and the restore unit — descriptions and selected words ride inside it rather than emitting
their own events.

**What Restore would need:** the door id, the contribution's descriptor and mode, its ordered units,
each unit's ordered ayahs, each ayah's word ids and ordered description bodies. That is exactly the
Stage-2 `after_state` document — which is the argument for making the contribution the aggregate
boundary in the first place.

## 15. Authorization

**Recommendation: Owner-only for the first release via `[RequireOwner]`; a `linking.*` permission
family as an explicit, separately-planned second step.**

Rationale:

- The Frontend is Owner-only today and re-checks the gate at every mutation and at mock confirmation.
  `[RequireOwner]` matches the proven product exactly and weakens nothing.
- Owner already bypasses every permission check anyway
  ([PermissionAuthorizationHandler.cs:35](Backend/api/QuranDashboard.Api/Authorization/Permissions/PermissionAuthorizationHandler.cs:35)),
  so an Owner-only v1 and a permissioned v2 are behaviourally identical for the only user who exists.
- Introducing `linking.*` codes is **not** additive: `AbwabPermissionCatalogue` is the single allowlist
  consulted by both the runtime handler and the startup validator, its static constructor asserts
  exactly 19 sequential codes across exactly 5 groups, and `AbwabPermissionCatalogueTests` pins
  `HaveCount(19)`. A second family needs a combined-catalogue seam
  (e.g. `IPermissionCatalogue` aggregating an Abwab and a Linking catalogue) threaded through the
  handler, the validator, `PermissionCatalogueSynchronizer`, and the AccessAdmin CLI's canonical-code
  list. That is a self-contained change, but it is a change, and bundling it into the first Linking
  slice would double its blast radius.
- When it lands, the natural codes are `linking.workspace.manage`, `linking.confirm`,
  `linking.edit`, `linking.delete`, `linking.restore` — mirroring the Abwab door verbs.

**Non-negotiables either way:** every unsafe Linking action carries exactly one classification
attribute (startup validation enforces it); the workspace read is authenticated and scoped to the
calling user's own row — never `?userId=`; and confirmation re-checks live access rather than trusting
that the workspace row exists.

## 16. Deferred read side

**Do not design the `GET existing links for a Door` API or read model in the implementation plan.**

The agreed sequence is: build and validate the Frontend presentation of a Door's existing links first,
then decide what read model that UI needs. This report deliberately stops at the write/storage,
source-resolution, caching, canonicalization, and workspace boundaries.

For information only — what a future read will obviously need from the model proposed here, so nothing
below blocks it:

- door → contributions → units → unit-ayahs, with ayah display metadata joined from `quran_ayahs`;
- selected words joined from `quran_words`;
- descriptions ordered by `order_value`;
- a `(door_id, deleted_at)` index on `linking_source_contributions` and an `ayah_id` index on
  `linking_unit_ayahs` for the reverse "which doors link this ayah" direction.

Those indexes are included in §17 because they cost nothing now. **No endpoint, no response DTO, and
no read caching strategy is specified here.**

## 17. Recommended data model

Two families, deliberately not merged. `W` = workspace state (mutable, per-user).
`C` = confirmed domain state (durable, per-Door).

---

### W1. `linking_workspaces`

| | |
| --- | --- |
| **Responsibility** | One per user; the concurrency anchor for the whole prepared workspace. |
| **Key** | `id bigserial` |
| **Columns** | `user_id int NOT NULL`, `created_at`, `updated_at`, `xmin` (`Version`) |
| **FKs** | `user_id` → `access_users(id)` RESTRICT |
| **Unique** | `UNIQUE (user_id)` |
| **Indexes** | the unique index suffices |
| **Lifecycle** | Never soft-deleted. Emptying it removes sources, not the row. |
| **Classification** | Workspace state |

### W2. `linking_workspace_sources`

| | |
| --- | --- |
| **Responsibility** | One prepared source with its complete configuration. |
| **Key** | `id bigserial` |
| **Columns** | `workspace_id`, `order_value int NOT NULL`, `source_kind text NOT NULL`, `source_identity text NOT NULL`, `label text NOT NULL`, `scope jsonb NOT NULL`, `root_id int NULL`, `lemma_id int NULL`, `stem_id int NULL`, `unique_simple_word_id int NULL`, `unique_tashkeel_word_id int NULL`, `word_type_tashkeel_word_id int NULL`, `inclusion_mode text NOT NULL`, `automatic_word_matches_enabled boolean NULL`, `manual_link_shape text NULL`, `last_resolved_count int NULL`, `last_resolved_at_utc timestamptz NULL`, `created_at`, `created_by`, `updated_at`, `updated_by`, `xmin` |

| **Lifecycle** | Hard delete (it is a draft). |
| **Classification** | Workspace state |

The two coherence checks are what make "impossible combinations unrepresentable" true in the database
as well as in the Frontend's TypeScript union.

Storing `ayah_id` rather than a `verseKey` string means the override set is FK-validated at write time

### W5. `linking_workspace_source_words`

| | |
| --- | --- |
| **Responsibility** | Manual selected words, already canonical. |
| **Key** | `(workspace_source_id, quran_word_id)` |

## 18. API / command boundaries

Three boundaries, deliberately minimal.

### 18.1 Source resolution

```
GET  /api/linking/sources/resolve?...            → complete resolved source (§3), ETag-conditional
POST /api/linking/sources/resolve                → same, for scopes too large for a query string
                                                   (Word Type carries ~11 discriminators)
```

Both authenticated and gated (§15). `POST` used as a read is a deliberate, documented exception — the
alternative is a fragile long query string. It must be marked so the unsafe-endpoint metadata
validator's classification stays honest.

### 18.2 Workspace persistence

```
GET    /api/linking/workspace                              → the caller's own workspace
PUT    /api/linking/workspace/sources                      → reorder (whole-workspace xmin)
POST   /api/linking/workspace/sources                      → add (idempotent by source_identity)
DELETE /api/linking/workspace/sources/{id}                 → remove
PUT    /api/linking/workspace/sources/{id}/configuration   → inclusion + word preference +
                                                             manual words + link shape (source xmin)
PUT    /api/linking/workspace/sources/{id}/descriptions    → whole per-ayah description set
DELETE /api/linking/workspace/sources                      → clear all
```

Recommendation: the configuration and description routes take a **whole replacement document per
source** rather than granular per-ayah patches. The Frontend already saves its manual word draft
atomically per source, and one document per source keeps the concurrency token meaningful.

### 18.3 Confirmation

```
POST /api/linking/operations   → ConfirmLinkingOperationCommand (§13)
```

One atomic command. This is the adapter that replaces `MockLinkingCommandPort`.

**Not designed here:** the Door-links read (§16), any approval/request workflow, any notification, and
any bulk edit of confirmed links.

## 19. Performance and scale

Realistic product usage: one Owner, a handful of prepared sources, occasional confirmations.

### 19.1 Query count

| Operation | Commands |
| --- | --- |
| Resolve a source, cold | 4–5 (existence, distinct-ayah set, ayah metadata, matched rows, word hydration) — the same bounded shape as the paged reads today, with `Skip/Take` removed |
| Resolve a source, warm backend cache | **0** |
| Resolve a source, warm frontend cache | **0 network** |
| Load workspace | 1 root + 5 child collections, or one `Include`-shaped query; bounded by ≤100 prepared sources |
| Confirm N sources | 1 idempotency probe + 1 door probe + N cached resolutions + 1 batched word validation + 1 batched ayah validation + the insert batch, all in one transaction |

**N+1 risks and how they are avoided:** never resolve per ayah (the existing `AyahWordHydration`
pattern loads all words for all page ayahs in one query — reuse it unpaged); never validate words one
at a time (`WHERE location = ANY(...)` / `WHERE id = ANY(...)` against the UNIQUE and PK indexes);
never load a contribution's children per contribution (batch by `source_contribution_id = ANY(...)`).

### 19.2 Payload and memory

| Source size | Ayahs | ≈Words | Uncompressed JSON | Compressed (est.) | Compact cache entry |
| --- | --- | --- | --- | --- | --- |
| Small | 10 | ~130 | ~25 KB | ~5 KB | ~1 KB |
| Medium | 200 | ~2,600 | ~450 KB | ~90 KB | ~21 KB |
| Large | 2,000 | ~26,000 | ~4 MB | ~800 KB | ~210 KB |

The 2,000-ayah row is the whole argument for §4.1's compact cache value and for enabling response
compression. Note the **absolute ceiling**: 6,236 ayahs / ~77,800 words ≈ 12 MB uncompressed — a
source matching the entire Quran is the worst case that a `MaxResolvedAyahs` guard exists for.

**Backend cache memory** with the compact representation and the shared ayah-text cache: on the order
of a few MB for a realistic working set, versus hundreds of MB if full DTOs were cached. With a
`SizeLimit` on the dedicated instance, the worst case is bounded by configuration rather than by usage.

**Frontend cache memory:** one complete source lives in `ApiResponseCache` as a parsed object graph,
roughly the uncompressed JSON size in the heap. This is why §4.2 recommends a cap of ~6–8 entries for
the Linking instance rather than the default 48.

### 19.3 Several sources at once, overlapping ayahs

Resolution is per source and independently cached, so a 3-source operation is 3 lookups (0 DB commands
warm). Overlap costs nothing at resolution — merging is a Frontend concern — and at confirmation
overlap produces more rows, not more queries, because everything is batched by contribution.

### 19.4 CDK virtualization boundary

The Frontend renders the complete set through one `cdk-virtual-scroll-viewport`. The Backend
contract that supports it is exactly §3: a complete, **stably ordered** set (Quran order:
`surah_number`, `ayah_number`) delivered once. Stable ordering is not optional — a virtual scroller
computes item offsets from index, so an unstable order corrupts the viewport rather than merely
reshuffling rows. The plan should treat "the resolution endpoint is deterministically ordered" as a
contract, and note that the CDK item template will have variable height (Quran text wraps), so the
Frontend will need `autosize` or a measured row rather than a fixed `itemSize`.

### 19.5 Transaction write size

A 3-source operation over ~50 ayahs with words and a few descriptions is on the order of a few hundred
inserts in one transaction — unremarkable for PostgreSQL. The pathological case (confirming a
2,000-ayah automatic source with all matched words) is ~2,000 unit rows + 2,000 unit-ayah rows +
~4,000 word rows. Still a single-digit-second transaction, but worth a stated `MaxAyahsPerOperation`
guard so it cannot grow silently. Batch the inserts (`AddRange`) rather than per-row `SaveChanges`.

### 19.6 What is deliberately not optimized

No partitioning, no materialized views, no read replicas, no denormalized link-count columns, no
covering indexes beyond those listed. The product has one Owner and a Hobby-tier single instance;
these would be premature.

## 20. Migration path from the current prototype

The V2 Frontend was built with replaceable seams. **Four adapter swaps, no rewrite.**

| # | Current | Replacement | Frontend blast radius |
| --- | --- | --- | --- |
| 1 | `LocalStorageLinkingWorkspaceRepository` | `HttpLinkingWorkspaceRepository` implementing the same `LinkingWorkspaceRepository` port (already `Promise`-returning) | **One file.** `LinkingWorkspaceStore` talks only to the port; components talk only to the store. The `linking-workspace.codec.ts` validation becomes unnecessary once the server owns validity, but can stay harmlessly as a defensive decoder. |
| 2 | 5 resolvers + `loadCompletePagedSource` walking explorer pages | One `LinkingSourceResolutionApi` behind the existing `LinkingSourceResolver` / `LinkingSourceResolverRegistry` | **The registry keeps its interface.** Every consumer (`LinkingSourceEditorFacade`, `LinkingSourceSetCoordinator`) calls `resolver.resolve(source, onProgress)` and is untouched. `complete-paged-source.loader.ts` and the five per-family resolvers are deleted. `onProgress` becomes a single 0→total tick or is dropped. |
| 3 | `presentation-occurrence` + `manual-word-location` word identities | `canonical-quran-word-id` only | `LinkingWordContribution` loses two of its three arms; `wordContributionsFor` simplifies to one branch. `LinkingAyahWord.canonicalQuranWordId` becomes non-nullable for automatic sources. **This also deletes the positional word-alignment guard in `linking-merge.ts`** — merging by canonical id is strictly safer than the current index-plus-text alignment. |
| 4 | `MockLinkingCommandPort` | `HttpLinkingCommandPort` implementing `LinkingCommandPort` via the `LINKING_COMMAND_PORT` injection token | **One provider swap.** `LinkingWorkflowFacade.submit()` already subscribes to an Observable and already handles success/error. The command already carries `{doorId, operation:{mergedSelection, sourceIntents}}` — the exact shape §13 needs. |

**What must change beyond the four swaps (and is already known):**

- Descriptions (§7) are new UI in the source-ayah editor, and new fields on `LinkingSourceConfiguration`
  and `LinkingIntentAyah` — identified in the current-state report as gap **G1**.
- CDK virtualization replaces the editor's client paging — gap **G2**. It should land with the
  descriptions work, since both reshape the same per-ayah row.
- The unrendered merged word union (gap **G4**) becomes trivially renderable once canonical ids exist.
- The manual Mushaf reader may keep composing study + page reads client-side, or move behind `/resolve`
  (§M-3).

**Order that keeps the app working at every step:** (2) resolution + canonical ids first — it is
invisible to the user but unlocks (3) and (4); then (1) workspace persistence; then (4) confirmation;
then descriptions + virtualization together. Swap (2) can ship before any table exists, because
resolution touches no Linking table at all.

The architecture is complete and grounded in the current codebase: the twelve-table model, the

Nothing here is `BLOCKED`: every open decision has a recommended default that the plan could adopt if

## C. Complete source-resolution architecture

One Linking-owned boundary returning the complete, deterministically Quran-ordered, validated ayah set
in a single ETag-conditional response, with canonical `quranWordId` on every word for every family.
Ordinary explorer pagination (100/page) is untouched; the Linking client stops walking it.

Caching is mandatory and three-layered:

1. **Backend source-truth cache** — dedicated size-limited `IMemoryCache`, key derived **only** from
   the typed source descriptor, value stored **compact** (ayah ids + word id arrays, ~20× smaller than
   the wire DTO), 30-min sliding, `Task<T>`-in-entry single-flight (**not** `CacheLoadGate`, whose own
   comment forbids caller-supplied key spaces), Uthmani text hydrated from a separate ayah-keyed cache
   that deduplicates across overlapping sources. **No Redis** — the deployment is single-instance and
   already cannot scale horizontally until the Abwab cache generation is shared.
2. **Frontend resolved-source cache** — a `LinkingSourceCache extends ApiResponseCache` with a
   ~6–8-entry cap (not the 48 default), so reopening a source or bouncing between editor and review
   costs zero network. `MushafReaderCache` reuse for manual sources stays as-is.
3. **Workspace persistence** — PostgreSQL, per-user, not a cache, never expires.

## D. Workspace persistence architecture

Six tables (§B), one row per user, mirroring the Frontend's proven state model: ordered sources, typed
descriptors, `all-except`/`only` inclusion as FK-validated `ayah_id` rows, automatic word preference,
canonical manual words, manual link shape, and draft descriptions. `xmin` at both workspace and source
grain; a stale token is `409`, never last-writer-wins. Transient UI state — checked sources, surface,
focus, search, viewport, review position, selected Door — stays client-side. Workspace state and
confirmed links never share a table.

## E. Confirmed linking write model

One atomic `POST /api/linking/operations` command: ten ordered validations (idempotency, actor, live
Door, descriptors, source membership by re-resolution, ayahs, canonical words, grouped-intent
cardinality, descriptions, uniqueness), then one explicit transaction inserting
operation → contributions → units → unit-ayahs → words → descriptions, with mandatory EF exception
translation (`23505` → `409`, concurrency → `409`) and all-or-nothing failure. No cache invalidation is
required, because confirmation writes no Quran data.

## F. Grouping / overlap semantics

`linking_units` is a real table. An automatic contribution emits one single-ayah unit per ayah; a
grouped manual contribution emits exactly one multi-ayah unit. Overlap is preserved by making
`(source_contribution, ayah)` the grain: `UNIQUE (source_contribution_id, ayah_id)` prevents an
intra-source duplicate while allowing the same ayah under two different contributions.
`[[A,B]]` + `[[A],[C]]` is stored as three units across two contributions and can never collapse into
`[[A,B,C]]` or lose the shared A.

## G. Selected-word canonicalization strategy

`quran_words.id` is the only durable word identity. Automatic sources become canonical by projecting
the `QuranWordId` that `AyahWordHydration` already loads (zero extra queries — the current Root/Lemma/
Stem DTOs simply drop it), which **eliminates the presentation-occurrence identity class entirely**.
Manual `wordLocation` is resolved to `quran_word_id` via the UNIQUE `quran_words.location` index at
**workspace save time**, so the workspace itself never stores a prototype coordinate. Every submitted
word id is validated as existing, non-marker, belonging to its declared ayah, and belonging to that
source's freshly resolved contribution. Render positions and array indexes are rejected at the API
contract.

## H. Per-source/per-ayah descriptions model

First-class rows on both sides (`linking_workspace_source_descriptions`,
`linking_unit_ayah_descriptions`), parented by `(source, ayah)` — never by the ayah. Surrogate id,
`order_value` resequenced 1..N (no unique index on it, matching the Abwab reorder precedent), plain
text `varchar(2000)`, non-blank check, bounded at 20 per `(source, ayah)`. Workspace side hard-deletes;
confirmed side soft-deletes so Restore has something to return. Cross-source merging is structurally
impossible because two sources contributing one ayah are two different parents.

## I. Audit / Restore integration

**There is no existing ChangeSet/Restore audit architecture to extend** — the only audit system is
`access_audit_events`, scoped to access administration, and no Abwab write emits an audit event.
Recommendation in two stages: **Stage 1 (required now)** — actually populate `created_by`/`updated_by`/
`deleted_by` (which Abwab leaves NULL everywhere), soft-delete every confirmed table, and use
claim-scoped restore exactly as `abwab.doors.restore` does. **Stage 2 (only on a real product
requirement)** — a `linking_audit_events` table copying the `access_audit_events` shape verbatim:
append-only enforced in `SaveChanges`, `jsonb` before/after/metadata with a numeric `schemaVersion`,
the two `CHECK` constraints, an appender enlisting in the caller's transaction, and a schema-drift
preflight entry. The contribution is the aggregate, so one document per contribution is both the change
unit and the restore unit.

## J. Authorization recommendation

**Owner-only via `[RequireOwner]` for the first release** — it matches the proven Frontend exactly,
weakens nothing, and requires no catalogue change. A `linking.*` permission family is the planned
second step and is **not additive**: `AbwabPermissionCatalogue` is the single allowlist consulted by
both `PermissionAuthorizationHandler` and the startup `UnsafeEndpointMetadataValidator`, its static
constructor asserts exactly 19 codes / 5 groups, and a test pins `HaveCount(19)`. Adding a second
family needs a combined-catalogue seam threaded through the handler, the validator,
`PermissionCatalogueSynchronizer`, and the AccessAdmin CLI. Every unsafe Linking action carries exactly
one classification attribute; the workspace read is scoped to the caller's own row, never
`?userId=`; confirmation re-checks live access.

## K. Performance / cache recommendations

**Backend source-result cache** — dedicated `IMemoryCache` with `SizeLimit` (never the shared instance:
setting a limit there breaks every existing size-less `Set`); key from the typed descriptor only, never
from user choices; compact int-based value (~210 KB for a 2,000-ayah source vs ~4 MB for the full DTO);
30-min sliding; `Task<T>`-in-entry single-flight; separate ayah-text cache deduplicated across
overlapping sources; no Redis.

**Frontend short-lived cache** — a Linking `ApiResponseCache` instance capped at ~6–8 entries; reopening
a source, editor↔review round trips, and client-side retries all become zero-network;
`MushafReaderCache` continues to serve the manual path.

**Workspace persistence** — PostgreSQL, per-user, not a cache, no expiry, no invalidation.

Plus: enable response compression (currently absent) before shipping a large resolution response;
guard with `MaxResolvedAyahs` and `MaxAyahsPerOperation`; batch every validation with `= ANY(...)`;
keep the resolution order deterministic because the CDK viewport depends on it.

## L. Deferred read-side work

**The `GET existing links for a Door` API and read model remain deferred and are deliberately not
designed here.** The Frontend presentation of a Door's existing links will be built and validated
first; only then will the exact read model and response DTO be decided. This report covers write and
storage architecture, source resolution, caching, workspace persistence, canonical word resolution, and
the confirmation command — and nothing else on the read side. The indexes a future read will obviously
want (`(door_id) WHERE deleted_at IS NULL`, `(ayah_id)`, `(quran_word_id)`) are included in §17 only
because they cost nothing now; no endpoint or DTO is implied by them.

## M. Decisions still requiring product-owner confirmation

Six genuinely unresolved decisions. Each has a recommended default the plan could adopt if no answer
arrives. No locked Frontend or product behaviour is reopened.

**M-1 · Description bound and length.** Recommended: max **20** descriptions per `(source, ayah)`,
body `varchar(2000)`, plain text. The numbers are product judgement, and the bound becomes a `CHECK`
constraint that is awkward to raise later.

**M-2 · Audit stage.** Ship Stage 1 only (attribution columns + soft delete + claim-scoped restore), or
build `linking_audit_events` in the same slice? Recommended: **Stage 1 only.** Stage 2 roughly doubles
the write slice and no product requirement for link history has been stated.

**M-3 · Manual Mushaf resolution boundary.** Should a manual source resolve through the same
`/api/linking/sources/resolve` endpoint, or keep composing the existing study + page reads client-side
(reusing `MushafReaderCache`)? Recommended: **serve it through `/resolve` too** — it unifies the client
contract, moves the seven-point completeness proof to the server where it can be trusted, and canonical
word ids come free. The cost is a Backend implementation of that proof, which currently lives only in
the Frontend.

**M-4 · Editing a confirmed contribution.** Is "change which ayahs this source contributes to this
Door" an in-place update of the live contribution, or a soft-delete plus a new confirmation? Recommended:
**in-place update** under the contribution's `xmin` (a new operation row records the edit). A
delete-and-recreate model would fragment description history across contribution ids.

**M-5 · Reseed-without-restart safety.** There is no data/import version marker anywhere, and no Quran
cache is invalidated today — the whole-summary caches have no expiry at all. Should Linking introduce a
one-row `quran_data_generation` table bumped by the importer and folded into the source-cache key?
Recommended: **no, not yet.** Match the existing posture (bounded staleness via 30-min sliding
expiry + restart-clears-all) and revisit when reseed-without-restart becomes a real operational
requirement, since a generation marker only helps if every Quran cache adopts it.

**M-6 · Permission family timing.** Ship Owner-only (§J) and add `linking.*` later, or build the
combined-catalogue seam in the same slice? Recommended: **Owner-only first.** Behaviourally identical
for the only user who exists, and it keeps the catalogue refactor as its own reviewable change.
