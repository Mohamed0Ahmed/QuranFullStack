# Feature 013 — Deterministic Unique Word IDs: Implementation Planning Report

> Planning report only. No source code was changed, no migration was created, no
> database writes were run. All schema facts below are read from the backend
> domain entities, EF Core configurations, the display-rebuild SQL + executor, the
> migrations list, the test fixtures, and the read-only database baseline reports
> (`Backend/report/database/current-database-tables-and-relationships-report.md`,
> `Backend/report/database-inventory/database-reset-and-seeding-order.md`).
> Companion: `feature-013-unique-words-capability-report.md`.

## 0. Verdict

**READY WITH NOTES.**

The product target is achievable with a small, low-risk, coherent change set and
**no data-backfill migration**:

- Set `quran_words_unique_tashkeel.id = first_quran_word_id` and
  `quran_words_unique_simple.id = first_quran_word_id`.
- `first_quran_word_id` already points to `quran_words.id`, a stable natural
  occurrence id (`ValueGeneratedNever`), and is **already deterministic across
  rebuilds** (derived from `ROW_NUMBER() OVER (ORDER BY id)` over the stable
  readable-word set). So `id = first_quran_word_id` is deterministic too.

The notes (none are blockers):

1. **Three edits are coupled and must ship together**: (a) EF config →
   `ValueGeneratedNever()` on both unique-table `Id`s; (b) one EF migration to drop
   the identity strategy from both PK columns; (c) rebuild SQL → explicitly insert
   `id = first_quran_word_id`. Applying any one without the others breaks the
   rebuild or the model/DB match. Tests catch this because they `MigrateAsync()`
   then run a real rebuild.
2. **The deterministic ids are realized by a rebuild**, not by the migration. The
   migration only removes identity generation; existing rows keep their old ids
   until `rebuild-words --force` re-inserts them. The final reset/reseed phase
   covers this.
3. **No DB FK** exists from `quran_words.unique_*_word_id` to the unique tables
   (only filtered indexes), so changing unique PK values is safe; link population
   already repoints them every rebuild.
4. **`first_quran_word_id` is kept** as a named, FK-backed column even though `id`
   now mirrors it. This redundancy is intentional (minimal change, existing readers
   use `first_quran_word_id`). Collapsing the two columns is **out of scope**.
5. **Adjacent ordered tables need no change** (see §5): their PK
   `word_order_in_mushaf` is already app-assigned, explicitly inserted, and
   deterministic; external code keys them by the stable `quran_word_id`.
6. **Pre-existing observation (out of scope):** the rebuild's informational warning
   `UNQ-EXPECT-TASHKEEL` expects 21,210 tashkeel rows
   (`DisplayWordsInvariants.InformationalUniqueTashkeel`) but the live DB has
   21,294. This is a warning-severity expectation only; it does not affect this
   change. Flag, do not fix here.

## 1. Current-state inventory (confirmed)

### 1.1 How the unique-table PKs are generated today

| Table | PK | EF config | DB generation | Insert behavior |
| --- | --- | --- | --- | --- |
| `quran_words_unique_tashkeel` | `id` | `builder.Property(x => x.Id).HasColumnName("id")` — **no `ValueGeneratedNever()`** (`UniqueTashkeelWordConfiguration.cs`) | EF default for an `int` key → **Npgsql identity-by-default** (`GENERATED BY DEFAULT AS IDENTITY`) | `DisplayWordsSql.InsertUniqueTashkeel` does **not** list `id`; DB assigns it |
| `quran_words_unique_simple` | `id` | same pattern (`UniqueSimpleWordConfiguration.cs`) | same — identity-by-default | `DisplayWordsSql.InsertUniqueSimple` does **not** list `id`; DB assigns it |

Corroboration that these are identity columns: `DisplayWordsSql.TruncateDerivedTables`
runs `TRUNCATE … RESTART IDENTITY`, which restarts owned identity sequences. By
contrast `OrderedTashkeelWordConfiguration` / `OrderedSimpleWordConfiguration`
explicitly call `.ValueGeneratedNever()` on their PK — proving the unique configs’
omission is what makes them identity-generated.

**→ Confirmed: unique-table ids are DB identity-generated and therefore NOT stable
across truncate+rebuild.** This is exactly the instability the product decision
targets.

### 1.2 How `DisplayWordsSql` inserts unique rows

From `DisplayWordsSql.InsertUniqueTashkeel` / `InsertUniqueSimple`
(`…/DataPipelines/Quran/Words/DisplayRebuilding/DisplayWordsSql.cs`):

- A `ranked` CTE over readable words (`is_ayah_marker = false`) assigns
  `word_order_in_mushaf = ROW_NUMBER() OVER (ORDER BY id)`.
- A `stats_*` CTE groups by identity (`text_uthmani` / `word_key_imlaei_simple`) for
  the three counters.
- A `first_occ` CTE uses `DISTINCT ON (identity) … ORDER BY identity,
  word_order_in_mushaf` to pick the **first occurrence** and captures
  `r.id AS first_quran_word_id` (+ first location/surah/ayah/page/line + display text).
- `INSERT INTO quran_words_unique_* (text/key, …, first_quran_word_id, …)
  SELECT …` — **`id` is omitted** (identity fills it).

The executor `SqlDisplayWordsRebuilder.RebuildAsync` runs everything in **one
transaction**: `NullQuranWordLinks` → (if force) `TruncateDerivedTables` → insert
ordered ×2 → insert unique ×2 → `UpdateUniqueTashkeelLinks` /
`UpdateUniqueSimpleLinks` → totals → hard checks → commit (or rollback on any hard
failure).

### 1.3 How `quran_words.unique_*_word_id` is populated

From `DisplayWordsSql.UpdateUniqueTashkeelLinks` / `UpdateUniqueSimpleLinks`:

```sql
UPDATE quran_words AS w
SET unique_tashkeel_word_id = u.id
FROM quran_words_unique_tashkeel AS u
WHERE w.is_ayah_marker = false
  AND u.text_uthmani = w.text_uthmani;          -- simple variant joins on word_key_imlaei_simple
```

- Links are set **only for readable rows** (`is_ayah_marker = false`); markers stay
  NULL (pre-nulled by `NullQuranWordLinks`).
- The link value is whatever `u.id` currently is. **This is the key reason the
  change is safe:** when `u.id` becomes `first_quran_word_id`, the same join sets
  the link to the deterministic id with **no change to the UPDATE statements**.

### 1.4 Constraints / indexes / FKs that interact

| Object | Where | Affected by this change? |
| --- | --- | --- |
| PK `quran_words_unique_tashkeel(id)` / `quran_words_unique_simple(id)` | unique configs | **Yes** — drop identity strategy; values become `first_quran_word_id` |
| Unique index `text_uthmani` (tashkeel), `word_key_imlaei_simple` (simple) | unique configs | No (identity keys unchanged) |
| Unique index `first_word_order_in_mushaf` (both) | unique configs | No |
| FK `quran_words_unique_*.first_quran_word_id → quran_words.id` (CASCADE) | unique configs / baseline FK inventory | No — different column from the PK; value unchanged |
| `quran_words.unique_tashkeel_word_id` / `unique_simple_word_id` | `QuranWordConfiguration.cs` | **No DB FK** — only filtered indexes `IX_quran_words_unique_tashkeel_word_id` / `…_simple_word_id` (filtered `is_ayah_marker = false AND … IS NOT NULL`). Confirmed: `QuranWordConfiguration` declares `HasOne` only for `Ayah` and `Page`; baseline FK inventory lists no FK from these columns. |

**→ Confirmed: there is no foreign-key constraint from `quran_words` to the unique
tables to drop/recreate.** The only schema object to alter is the identity strategy
on the two PK columns.

## 2. Target design

Goal: deterministic, reproducible unique-word ids equal to the first-occurrence
`quran_words.id`.

1. **Application-assigned PKs.** In `UniqueTashkeelWordConfiguration` and
   `UniqueSimpleWordConfiguration`, add `.ValueGeneratedNever()` to the `Id`
   property (mirroring the ordered-table configs). EF will then expect the
   application to provide `id`.
2. **Explicit `id` in rebuild SQL.** Change `InsertUniqueTashkeel` /
   `InsertUniqueSimple` to insert `id` from the already-computed
   `first_occ.first_quran_word_id`:

   ```sql
   INSERT INTO quran_words_unique_tashkeel (
     id, text_uthmani, text_uthmani_simple, text_imlaei_simple,
     occurrences_count, ayahs_count, surahs_count,
     first_quran_word_id, first_location, first_surah_number, first_ayah_number,
     first_word_order_in_mushaf, first_page_number, first_line_number
   )
   SELECT
     f.first_quran_word_id,        -- id := first_quran_word_id (deterministic)
     f.text_uthmani, …, f.first_quran_word_id, …
   FROM first_occ f
   JOIN stats_tashkeel s ON s.text_uthmani = f.text_uthmani
   ```

   (Simple variant identical, joining on `word_key_imlaei_simple`.) No other CTE
   changes are needed — `first_quran_word_id` is already selected.
3. **Link population unchanged.** `UpdateUniqueTashkeelLinks` /
   `UpdateUniqueSimpleLinks` keep joining on the identity text and `SET … = u.id`;
   `u.id` is now `first_quran_word_id`, so links automatically become deterministic.
4. **Ayah markers stay NULL.** Unchanged: `NullQuranWordLinks` then update only
   `WHERE is_ayah_marker = false`. Invariants `LINK-MARKERS-NULL` /
   `LINK-READABLE-COMPLETE` continue to guard this.
5. **No change** to Quran text, word text, counters
   (`occurrences/ayahs/surahs_count`), identity keys (`text_uthmani`,
   `word_key_imlaei_simple`), `first_*` fields, or ordered tables.
6. **`TruncateDerivedTables`**: `RESTART IDENTITY` becomes a no-op for the unique
   tables once they are non-identity (still valid SQL; harmless for the ordered
   tables which remain app-assigned). May keep as-is or drop the clause; keeping it
   is lowest-risk. (Decision item §8.)

**Correctness of `id = first_quran_word_id` as a PK (uniqueness):** each unique row
is one identity (`DISTINCT ON (identity)`), and every `quran_words` row maps to
exactly one identity, so two identities can never share a first occurrence →
`first_quran_word_id` is unique per table → valid PK. Gaps are expected and
acceptable (only ~21,294 / ~14,783 of the 77,432 readable ids are first
occurrences).

**Determinism argument:** `quran_words.id` is stable (`ValueGeneratedNever`, natural
source id) and `is_ayah_marker` is stable, so the readable set and its
`ROW_NUMBER() OVER (ORDER BY id)` are identical every rebuild ⇒ each identity’s
earliest occurrence (`first_quran_word_id`) is identical ⇒ `id` is identical every
rebuild/reset/reseed.

## 3. Migration strategy

### 3.1 Is an EF migration required?

**Yes.** Removing identity generation from a PostgreSQL column is a schema change
(`ALTER COLUMN … DROP IDENTITY`). Changing only the EF `ValueGeneratedNever()`
annotation without a migration would make the model and the database disagree
(the DB column would still be `GENERATED BY DEFAULT AS IDENTITY`).

Per `Backend/CLAUDE.md`: migrations are generated with EF tooling
(`./scripts/add-mig <Name>`), only on explicit request, never hand-written. **This
plan does not create it.**

### 3.2 Safest approach

- One migration covering **both** PK columns (e.g. `DeterministicUniqueWordIds`),
  generated by EF after the two config `.ValueGeneratedNever()` edits, via
  `./scripts/add-mig DeterministicUniqueWordIds`.
- Expected generated change: `AlterColumn<int>("id", "quran_words_unique_tashkeel"/
  "quran_words_unique_simple", …)` dropping the
  `Npgsql:ValueGenerationStrategy = IdentityByDefaultColumn` annotation (the
  `OldAnnotation` records the prior identity; the new column has no generation
  strategy). No table rewrite, no data loss, no FK drop/recreate (none exist on the
  PK; the `first_quran_word_id` FK is unaffected).
- **No data backfill in the migration.** Existing identity-generated ids remain
  valid integers until the next `rebuild-words --force` re-inserts deterministic
  ids. Do **not** attempt an in-migration `UPDATE id = first_quran_word_id` (it is
  unnecessary and risks transient PK collisions). The reseed realizes the new ids
  (§7).
- **Coupling/ordering:** ship config + migration + rebuild-SQL together. After the
  migration, a rebuild that still omitted `id` would fail (no default) — so the SQL
  change must be in the same change set. After the migration, a rebuild **must** be
  run to materialize deterministic ids.
- Review the generated `.cs` + designer + `…ModelSnapshot.cs` to confirm only the
  two identity annotations changed and report the migration name/files/build/test
  status (per `Backend/CLAUDE.md` "Definition of Done" for migrations).

### 3.3 FK accounting

- `quran_words.unique_tashkeel_word_id` / `unique_simple_word_id` → **no FK**; only
  filtered indexes. Nothing to drop/recreate. Links are repointed by the rebuild’s
  UPDATEs every run.
- `quran_words_unique_*.first_quran_word_id → quran_words.id` (CASCADE) → unaffected
  (separate column, value unchanged).

### 3.4 Test database / schema setup

- Tests provision a real PostgreSQL via **Testcontainers** (`postgres:16-alpine`)
  and apply schema with **`dbContext.Database.MigrateAsync()`**
  (`WordsDisplayTestFixture`, `DisplayWordsRealImportFixture`, and the other
  `*ImportTestFixture`s). So the new migration is picked up automatically — **no
  bespoke test-schema wiring needed.**
- `WordsDisplayTestFixture.TruncateAllAsync` uses `TRUNCATE … RESTART IDENTITY
  CASCADE`; still valid after the unique tables become non-identity (no-op for their
  sequences). The synthetic seed path (`SeedDefaultSyntheticDataAsync` →
  `RebuildDisplayWordsHandler`) exercises the new explicit-`id` insert.
- No production/shared DB action in tests; everything is ephemeral per fixture.

## 4. Validation and hard checks

### 4.1 New hard checks to add to the rebuild (`SqlDisplayWordsRebuilder` + `DisplayWordsSql`)

Add as **hard** severity so a violation rolls back the rebuild (consistent with the
existing check pattern; each is `SELECT COUNT(*)::int … = 0`):

| Proposed id | Assertion | SQL sketch |
| --- | --- | --- |
| `UNQ-ID-DETERMINISTIC` | every unique row has `id = first_quran_word_id` (both tables) | `SELECT (SELECT COUNT(*) FROM quran_words_unique_tashkeel WHERE id <> first_quran_word_id) + (SELECT COUNT(*) FROM quran_words_unique_simple WHERE id <> first_quran_word_id)` → expect 0 |
| `UNQ-ID-UNIQUE` (optional; PK already guarantees) | no duplicate ids | `COUNT(*) − COUNT(DISTINCT id)` per table → expect 0 |

Existing hard checks already cover the rest and must keep passing unchanged:
`LINK-READABLE-COMPLETE` (every readable word has both links non-null),
`LINK-MARKERS-NULL` (markers null), `LINK-RESOLVES` (links resolve to a unique row),
`LINK-CONSISTENT` (tashkeel link ⇒ `u.text_uthmani = w.text_uthmani`; simple link ⇒
`u.word_key_imlaei_simple = w.word_key_imlaei_simple`), `STAT-MATCH` (counters),
`FIRST-OCC` (first_* matches earliest ordered row), `SRC-UNTOUCHED` (source
word/ayah/surah counts unchanged), `UNQ-COUNT` (row counts = distinct identities).

### 4.2 Test plan (extend the existing `WordsDisplay` suite)

The suite already has the right fixtures and homes — extend, don’t duplicate:

| Requirement | Test home | Approach |
| --- | --- | --- |
| every `unique_tashkeel.id = first_quran_word_id` | `DisplayWordsIdentityLinksTests` / new `DisplayWordsDeterministicIdTests` | after rebuild, assert `id == first_quran_word_id` for all rows |
| every `unique_simple.id = first_quran_word_id` | same | same |
| no duplicate ids | same | `id` distinct count == row count |
| readable rows have non-null links | `DisplayWordsIdentityLinksTests` (exists) | keep/confirm |
| ayah markers have null links | `DisplayWordsIdentityLinksTests` (exists) | keep/confirm |
| all links resolve | `DisplayWordsIdentityLinksTests` (exists) | keep/confirm |
| link consistency (tashkeel=`text_uthmani`, simple=`word_key_imlaei_simple`) | `DisplayWordsIdentityLinksTests` (exists) | keep/confirm |
| **rebuild twice ⇒ same unique ids** | `DisplayWordsIdempotencyTests` (exists) | snapshot `(id ↔ text_uthmani)` / `(id ↔ word_key_imlaei_simple)` after rebuild #1, force-rebuild, assert identical mapping **and** that links still point to the same ids |
| source text columns unchanged | `DisplayWordsSourceUntouchedTests` (exists) + `SRC-UNTOUCHED` | keep/confirm |
| counters unchanged | `DisplayWordsStatisticsTests` (exists) | keep/confirm |

Run with the real-import fixture too (`DisplayWordsRealImportFixture` /
`DisplayWordsRealImportIdentityLinksTests`) so determinism is validated against the
canonical source, gated by `CanonicalImportSourceTestGate`. Honor the project’s
test-worker cap when running (`VITEST` cap is frontend; backend tests are xUnit but
keep the machine’s usual constraints in mind).

## 5. Adjacent ID review — `quran_words_ordered_tashkeel` / `quran_words_ordered_simple`

| Question | Finding |
| --- | --- |
| IDs identity-generated or derived? | **Derived / app-assigned.** PK is `word_order_in_mushaf` with explicit `.ValueGeneratedNever()` (`OrderedTashkeelWordConfiguration.cs`); the value is inserted from `ROW_NUMBER() OVER (ORDER BY id)` in `DisplayWordsSql.InsertOrderedTashkeel/Simple`. Not a DB identity column. |
| Deterministic across rebuilds? | **Yes.** `ROW_NUMBER() OVER (ORDER BY id)` over the stable readable set is reproducible; same value every rebuild. |
| Used by links / URLs / APIs / planned UI? | The ordered tables are read by `quran_word_id` (the unique stable natural key — see `EfWordAnalysisReader`), **not** by `word_order_in_mushaf` as an external identifier. Feature 013 unique-words UI does not key off ordered ids. They also expose `quran_word_id` (unique) as a stable alternate key. |
| Should they change now? | **No — out of scope.** No identity instability (already app-assigned + deterministic) and no external dependency on the PK value. There is no correctness/stability issue to fix. Broadening scope would add migration/test churn with no benefit. |

(If a future feature ever exposes `word_order_in_mushaf` as a durable external id,
revisit — but it is positional/dense-rank, not a natural occurrence id; prefer
`quran_word_id` for any such need.)

## 6. Phase-by-phase implementation plan

**Phase 1 — Inspection & final design confirmation.** Confirm the §1 findings on
the actual branch (config omission of `ValueGeneratedNever`, insert SQL omitting
`id`, link UPDATEs, absence of `quran_words → unique` FK). Confirm the §8 decisions
(keep `first_quran_word_id`; keep/drop `RESTART IDENTITY`). No code yet.

**Phase 2 — EF/entity/config + migration.** Add `.ValueGeneratedNever()` to `Id` in
both unique configs. Generate one migration via `./scripts/add-mig
DeterministicUniqueWordIds`; review the generated `.cs`/designer/snapshot to confirm
it only drops the two identity annotations (no rewrite, no FK change). Do not run
`update-db` against a shared DB.

**Phase 3 — Rebuild SQL changes.** Add `id` (= `first_quran_word_id`) to the column
list and `SELECT` of `InsertUniqueTashkeel` / `InsertUniqueSimple`. Leave ordered
inserts, link UPDATEs, and counters untouched. Decide on `RESTART IDENTITY`.

**Phase 4 — Validation / tests.** Add the `UNQ-ID-DETERMINISTIC` hard check (and
optional `UNQ-ID-UNIQUE`) to `DisplayWordsSql` + `SqlDisplayWordsRebuilder`
`RunHardChecksAsync`. Add/extend the `WordsDisplay` tests in §4.2 (synthetic +
real-import). Run the clean-code and test-guard self-checks per the workspace
instructions.

**Phase 5 — Build / test / report / review.** `./scripts/qd-build`; run the backend
test suite (Testcontainers will apply the new migration). Write the backend report
under `Backend/report/feature-013-…/` (migration name, files, build/test status,
checks). Then the formal `engineering-review` skill.

**Phase 6 — Local reset/reseed verification.** Execute §7 end-to-end on the local
DB and verify deterministic ids + all hard checks. This is the acceptance gate.

## 8. Risks and decisions needed

| # | Risk / decision | Recommendation |
| --- | --- | --- |
| R1 | Coupling: config + migration + SQL must land together, else rebuild fails (id has no default) | Ship as one change set; rely on Testcontainers `MigrateAsync` + rebuild to catch drift |
| R2 | Migration applied but no rebuild run ⇒ old non-deterministic ids persist | Make `rebuild-words --force` a required post-migration step; enforce via the §7 gate and the new hard check |
| R3 | Keep vs collapse `first_quran_word_id` now that `id` mirrors it | **Keep** `first_quran_word_id` (FK-backed, used by readers); collapsing is out of scope |
| R4 | `RESTART IDENTITY` in `TruncateDerivedTables` after columns become non-identity | Harmless no-op; keep as-is (lowest risk) — or drop the clause. Decision item, not a blocker |
| R5 | Saved/bookmarked unique-word ids from before the change become different values after reseed | Expected and accepted (gaps/values change once, then stable). Capability report already advises natural keys for durable deep-links |
| R6 | Pre-existing `UNQ-EXPECT-TASHKEEL` warning (expects 21,210, DB has 21,294) | Out of scope; note only. Do not change the informational constant in this work |
| R7 | Determinism depends on `quran_words.id` + `is_ayah_marker` stability | Holds (foundation import is deterministic; `id` is `ValueGeneratedNever`). The second-rebuild check (§7.5) guards regressions |

### Decisions to confirm before Phase 2
1. Migration name (suggested `DeterministicUniqueWordIds`).
2. Keep `first_quran_word_id` column (recommended yes).
3. Keep or drop `RESTART IDENTITY` in `TruncateDerivedTables` (recommended keep).
4. Add optional `UNQ-ID-UNIQUE` hard check in addition to `UNQ-ID-DETERMINISTIC`
   (recommended: yes, cheap defense-in-depth even though the PK guarantees it).

## 9. Scope boundaries

**In scope:** deterministic ids for `quran_words_unique_tashkeel` /
`quran_words_unique_simple` (`id = first_quran_word_id`); the EF config +
single migration; the `InsertUniqueTashkeel`/`InsertUniqueSimple` SQL change;
link-population continuity; new `UNQ-ID-DETERMINISTIC` (and optional
`UNQ-ID-UNIQUE`) checks; extending the `WordsDisplay` tests; backend report;
final local reset/reseed verification.

**Out of scope:** Words UI/API implementation; `/dashboard/words` route change;
pagination/search; optional composite drill-down indexes (not required for
correctness here); changing counters, Quran/word text, identity keys, `first_*`
fields; ordered-table ids; morphology/i3rab/tafsir/translation data; collapsing the
redundant `first_quran_word_id` column; the pre-existing `UNQ-EXPECT-TASHKEEL`
informational-count discrepancy.
